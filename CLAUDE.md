## Project Overview

A lightweight Three.js viewer designed to be controlled from Python/Jupyter notebooks. Primary use case: visualizing 3D data and animations at 60fps. The browser viewer persists across Python script restarts.

## Architecture

### Tech Stack
- **Viewer**: Static HTML/JS (no build tools, no Node, no frameworks)
- **Three.js**: Loaded from CDN (unpkg)
- **Python**: WebSocket server via `websockets` library

### Core Files
- `src/threejs_viewer/client.py` - Python client that runs WebSocket server
- `src/threejs_viewer/animation.py` - Animation classes (Frame, Animation, AnimationChannel, Marker)
- `src/threejs_viewer/viewer.html` - Standalone viewer (**generated** — do not edit, run `uv run python src/threejs_viewer/viewer/build.py` to regenerate)
- `src/threejs_viewer/viewer/` - Viewer source files (edit these):
  - `viewer.js` - ES module exporting `ThreeJSViewer(container, options)`. Internal structure: `ThreeJSViewer` orchestrates several in-file controller classes — `ParametricTube` (per-tube geometry + LOD + morph state), `CameraController` (perspective/ortho cameras, framing, scene bounds), `ShadingDebugController` (M/N debug cycles). Clipping and animation subsystems are grouped under banner comments (`// ========== Clipping ==========` / `// ========== Animation ==========`) rather than classes. All controllers live in a single file on purpose: `build.py` is concat-only and the viewer ships as one `<script>` block. Ring/color helpers for parametric tubes are free functions at the top of the file (`writeRingVerts`, `writeCapRingVerts`, `fillRGBBlock`, `sampleChamferedRect`, `distanceWeightedRDP`) — shared between the main thread and the inlined LOD worker source. Typed via JSDoc + `// @ts-check`; run `npx tsc --noEmit -p jsconfig.json` to type-check.
  - `viewer.css` - Scoped CSS under `.threejs-viewer` class
  - `template.html` - HTML template for toolbar, clipping panel, animation controls
  - `build.py` - Build script that inlines all sources into standalone `viewer.html`
  - `static/*.jpg` - Cubemap face images for PBR environment
- `examples/` - Demo scripts showcasing library capabilities
- `tests/` - Unit tests + Playwright browser integration tests (browser tests auto-skip without pytest-playwright)
- `plans/` - Decision-making artifacts for undecided future work (NOT landed architecture). Each file documents its own status. Skip when looking for current architecture; consult only when picking up an open decision.

### Communication Model
- **Direct connection**: Python runs WebSocket server on port 5666 (default), browser connects to it. Port is overridable via `?ws_port=` query param in viewer URL.
- **Browser survives restarts**: Viewer auto-reconnects when Python script restarts
- **Binary transfer**: Large data (models, polylines, animations) served via HTTP sidecar on port 5667, browser fetches with native `fetch()`
- **Batch updates**: `batch_update()` updates multiple objects in one message
- **60fps capable**: Minimal JSON payloads with 4x4 matrices
- **Embedder camera/pick/controls API** (issue #77): `viewer.getCameraPose()` → `{position, target, up, fov, zoom}` (`fov` null under ortho); `viewer.setCameraPose({position, target, up, fov, zoom})` — one-shot partial pose set, vectors accept `{x,y,z}` or `[x,y,z]`, explicitly `lookAt`s the target (ViewerControls never re-orients itself) and is also the implementation behind the `set_camera` WS case so the two can't drift; `viewer.frameBox(min, max, margin=1.5)` — fit the camera to a world AABB (`frameObject` for a box); `viewer.pick(clientX, clientY, {pointsThreshold, ids})` — raycast **meshes + point clouds** (lines excluded on purpose — `enablePolylinePicking` is the arc-length-aware path) from viewport coords, skips hidden subtrees, resolves the **top-level tracked id** by walking ancestors (a GLTF sub-mesh reports its model's id), returns `{point, objectId, distance, object3D}` of the nearest hit or `null`; `viewer.setControlsEnabled(bool)` — suppress orbiting while an embedder drags its own handle. All JS-only (no Python/WS surface beyond the existing `get_camera`/`set_camera`).
- **Embedder animation/object/overlay/status API** (issues #74/#75/#76/#78): `viewer.seekAnimationTime(s)` / `getAnimationState()` → `{time, duration, playing, speed, loop}` (null when no animation) / `setAnimationPlaying(bool)` / `setAnimationSpeed(mult)` (parks the native ± stepper on the nearest predefined step) / `onAnimationTime(cb)` (fired with the full state on every applied frame — playback tick, seek, frame step — and on play/pause flips; returns an unsubscribe fn; saves embedders a rAF poll) — all around the **one shared clock** that also drives draw_range reveals and follow-path tracks. `viewer.getObject(id)` → the loaded `THREE.Object3D` (escape hatch: the viewer guarantees the id mapping, not the object's internals), and **`handleMessage()` returns the reply payload** for query messages (`list_objects`/`query_scene`/`get_camera`) via a `_reply()` capture, so no-WS embedders get answers as the resolved value. `viewer.addOverlay(object3D, {id, includeInBounds})` / `removeOverlay(idOrObject)` — embedder-owned scene mounts: excluded from framing/scene bounds unless `includeInBounds: true`, untouched by scene `clear` and the animation system, never disposed by the viewer (re-using an id replaces). `viewer.setStatus(text, state)` (`connected`/`disconnected`/`neutral`) drives the header chip, which under `autoConnect: false` now defaults to a neutral "Local data" instead of "Waiting for Python...".
- **WS-decoupled dispatch**: The control-message switch lives in a public `viewer.handleMessage(data)` method; `connect()`'s `onmessage` only parses the WS frame and delegates to it. This makes no-WebSocket / static-page embedding first-class — construct `new ThreeJSViewer(container, { autoConnect: false })` (already supported) and feed messages straight in (`viewer.handleMessage({ type: 'add_points_binary', id, blob_url, ... })`) with no `websockets` server. Binary payloads still load over HTTP (static files or in-page `Blob` object URLs) exactly as under the socket transport. Query messages that expect a reply (`list_objects`, `query_scene`, `get_camera`) route their response through `_reply(payload)`, which sends over the socket when one is connected and always returns the payload — the query cases return it straight out of `handleMessage()`, so no-WS embedders get the answer as the resolved value (per-invocation, no shared capture state).

### Animation Modes
- **Streaming mode**: Real-time updates from Python (`batch_update()`, `set_matrix()`)
- **Looping mode**: Pre-computed frames with interactive playback (`load_animation()`)

### Animation lifecycle
- **`load_animation(anim)`** — first call (no animation loaded yet) starts at t=0; playback begins immediately unless `autoplay=False`. Subsequent calls preserve the current playhead time (clamped to the new duration), play state, and camera-tracking — only the underlying frame data is swapped. Pass `restart=True` to force the first-load behavior (reset to t=0, re-install camera-tracking) on a swap; `autoplay` still governs play/paused on a restart. `autoplay=False` has no effect on a swap without `restart` (prior play state is preserved). Pass `initial_time=<seconds>` or `initial_time="end"` to land the playhead at a chosen time on first load / restart (ignored on a swap) — pairs with `autoplay=False` for "paused at completion". Pass `loop=True|False` to override the animation's baked `loop` flag (omit to use `anim.loop`).
- **`pause_animation()` / `resume_animation()`** — pause/resume at the current playhead. No-op if no animation loaded.
- **`unload_animation(restore_visibility=True)`** — exit animation mode entirely: re-enables `matrixAutoUpdate` on every object (animation pins it off), resets every draw range to 1.0, optionally restores baseline visibility, hides the controls UI. This is **not** a pause. Replaces the older `stop_animation()` / `clear_animation()` (use `restore_visibility=False` for the old `clear_animation` semantic).
- **`set_follow_path(id, times, positions, axes)`** — attach a *follow-path track*: object `id` rides a timed 5-axis path, its pose computed **per render tick from the real path** at the current animation time (binary search on `times`, tip position lerped, tool axis nlerped, minimal rotation of the object's local `+z` onto the axis; the object's own scale is preserved). Use it for a 1:1 tool body: animation frames may sample a long timeline coarsely (e.g. 10 Hz `transforms`), but the tracked object still hits every path point exactly — no keyframe aliasing on a fast toolpath. Payload is binary (`(K,)` non-decreasing **float64** seconds followed by `(K,3)` tip positions + `(K,3)` unit axes packed as float32 `[px,py,pz,ax,ay,az]` rows, K≥2, fetched via the blob sidecar). Times are float64 on purpose: float32's ulp is ~4 ms at t=40,000 s and ~16 ms at 160,000 s, which on hours-long timelines jitters the tool visibly and collapses ms-spaced keys to dt=0 (hold-then-jump stutter); positions/axes stay float32 (mm-scale geometry is fine). The track drives the object whenever an animation is loaded (it reads the animation clock; it composes `obj.matrix` directly with `matrixAutoUpdate` pinned off, overriding any `transforms` channel for that id). Tracks are per-id (a re-send replaces), dropped on `delete`/`clear`, and follow-path objects are the **preferred camera-tracking target**: the `T` track cycle (off → follow → look-at) picks a follow-path id before falling back to transform-channel name hints (`nozzle`/`tip`/`tool`/`effector`).

### Supported Object Types
- **Groups**: `add_group(id, parent=...)` — empty transform nodes for parent-child hierarchies. Children inherit parent transforms. All `add_*` methods accept an optional `parent` parameter.
- Primitives: box, sphere, cylinder, capsule (with optional roughness/metalness)
- Polylines: gradient-colored with colormaps (viridis, plasma, turbo). `add_polyline(..., fat=False)` renders a native `THREE.Line` (one vertex per point, ~1px, one draw call) instead of the default fat `Line2` — far lighter for million-point toolpaths, but WebGL ignores `line_width`. Per-vertex colors, `set_draw_range`, the `draw_ranges` channel, and `update_polyline_colors` work on both paths. `add_polyline(..., segments=True)` renders disjoint line *segments* instead (`THREE.LineSegments`: consecutive point pairs each draw an independent edge) — many separate episodes in one object/draw call with no false connectors; requires an even point count, implies the native path (`fat` ignored), and is never pickable (an edge soup has no arc length).
- Meshes: pre-built triangle meshes via `add_mesh()` with optional vertex colors and normals
- Beads: toolpath extrusion via `Toolpath` + `add_toolpath()` — convenience wrapper around `add_parametric_tube` with colorize support. Zero-width segments (travel moves) collapse to degenerate points for natural taper transitions. **Travel-move rendering** (issue #88): `add_toolpath(..., travel="line", travel_color=0x666666)` also draws the travel hops themselves — every spine edge not interior to an extrusion run (each hop spans from the last extruded point through the zero-width points to the next extruded point) as **one** `segments=True` native line child (`<id>_travel`, single draw call for any number of disjoint episodes). Wired into the group's draw-range distribution by contract: `register_toolpath_group` carries `travelId` + ascending `travelEndFracs` (global spine fraction of each edge's end point, same `/n_total` convention as `segmentRanges`), and `applyToolpathGroupDrawRange` binary-searches them to reveal whole hop edges in lockstep with the beads — robust where the draw-a-line-under-the-bead occlusion trick broke (`opacity < 1`, LOD thinning). With `travel="line"` even a single-run toolpath with travel gets the group form (the bare-tube fast path has nowhere to hang the mapping); without travel stretches the option is a no-op. See `examples/15_toolpath_interrupted.py`.
- **Parametric tubes**: `add_parametric_tube(id, spine, widths, heights, colors=..., anchor="center")` — variable-cross-section extruded tube built on the client from per-spine-point parameter arrays. Chamfered hexagonal cross-section (45° chamfers, 6 vertices per ring) with constant-up frame derivation (V anchored to global +Z). Corner handling: directional miter — the cross-section stretches by 1/cos(half-turn) along the actual turn direction projected into the section plane (so vertical layer-change elbows stretch along V instead of flaring sideways), bevel past `TUBE_MITER_LIMIT = 2` (turns sharper than 120°; exactly-120° sits on the strict gate boundary and may resolve either way per float rounding); frames freeze across near-vertical tangent runs (|T·up| > 0.99 — interior riser samples copy the nearest out-of-cone neighbor's frame instead of seeding V from the fallback axis); and a deposition-order bias scales each ring up by ≤0.1% about its anchored section centre (per-ring anchor offsets `vOffs` are captured from the unbiased heights, so the anchored face separates too) so an exact retrace (A→B→A) nests the later-deposited leg outside the earlier one — the visible surface is deterministically the last bead laid; `add_toolpath` threads one global ramp across travel-split segment tubes via `bias_index_offset`/`bias_index_total`. `anchor="center"` (default) centers the bead on the spine; `anchor="top"` places the spine at the top surface so the bead extends downward (useful when the spine represents a nozzle-tip toolpath). Revolution surface end caps. Supports `draw_range` with smooth frontier-ring morphing (the next ring's vertices are lerped to the interpolated spine position for pixel-smooth growth), the `draw_ranges` animation channel, and cheap color-mode swaps via `update_parametric_tube_colors(id, colors)`. **LOD**: tubes with ≥25k spine points get automatic distance-weighted RDP simplification — a Web Worker runs chunked RDP (chunk size 5000, epsilon = camera_distance / 2500) and builds the reduced geometry off the main thread. Per-chunk results are cached and reused when the camera distance to the chunk midpoint changes less than 50%. Chunks are sequential spine spans (not spatial), which is required to preserve draw_range ordering and frontier morphing continuity. LOD updates are throttled to 2 Hz. Per-tube LOD overrides via the optional `lod=` kwarg on `add_parametric_tube` (also passes through `add_toolpath(**kwargs)`): pass `lod=False` to disable entirely, or `lod={"epsilon_divisor": N, "threshold": M}` to tune detail retention and the spine-length gate (use `threshold=0` to force LOD on below 25k).
- **Swept tool body (5-axis)**: `add_swept_tool(id, positions, axes, profile, colors=..., sections=16, color=..., opacity=1.0, metalness=.., roughness=..)` — swept *oriented* tool-body tube for 5-axis toolpaths. The crux vs `add_parametric_tube`: it **decouples the extrusion axis from the path tangent**. At each station `k` the `(height_along_axis, radius)` `profile` (M×2, revolved into rings of `sections` verts) is lofted about the **tool axis** `axes[k]` (unit, tip→holder — generally *not* the path tangent), centred at `positions[k]`, and consecutive stations are connected into a swept surface (the swept shank/holder of a tilting tool — reveals reorientation-rate "wrist speed" and tool-body collisions the cutting-tip envelope can't). Geometry built client-side by the in-file free function `buildSweptToolGeometry`: per densified profile level a ring is lofted along the path (per-level swept tube), straight profile runs are **densified in height** so a sparse profile still sweeps a continuous wall, with revolution end caps at the first/last station; a per-station constant-up frame (V anchored to +Z, +X fallback near-vertical) keeps rings from twisting. Per-station `colors` are packed `uint32 0x00RRGGBB` (like the tube), linearly interpolated along the path; `MeshStandardMaterial` (DoubleSide, `opacity<1` → translucent so the part shows through for collision reads). Index order is station-major so `set_draw_range`/`draw_ranges` reveals the body along the path (`userData.isSweptTool` + `totalIndexCount`). The linear loft can pinch/self-intersect on the inside of a sharp axis swing — accepted (faithful surface, not a boolean solid). Tool-body picking and LOD are not wired for this primitive.
- **Point clouds**: `add_points(id, positions, colors=..., colormap=..., color=0xFFFFFF, size=2.0, size_attenuation=True)` — GPU point cloud rendered as a single `THREE.Points` draw call (native `THREE.PointsMaterial`), for massive unconnected clouds (voxel fields, metrology/deviation clouds, LiDAR scans) where `add_polyline` would wrongly connect points and one primitive per point is too heavy. Binary transfer of `positions (+ colors)` like `add_polyline`; per-point colours via the same `_apply_colormap` path (scalar→colormap, or `(N,3)` RGB, or a flat `color` fallback when `colors=None`). `size` is the base point size in px; `size_attenuation=True` (default) shrinks points with distance (perspective, viewport-aware), `False` draws a constant pixel size. Supports `set_draw_range`/`draw_ranges` (reveals the leading `frac*N` points of the buffer — order points along a toolpath for a cheap material-removal animation). Flat `THREE.Points` covers ≤~10M points comfortably; larger clouds use the octree LOD tier below. Picking is not wired for points (the arc-length `PolylinePickController` is spine-based). **Per-point time window**: `add_points(..., birth_times=..., removal_times=...)` attaches optional (N,) per-point lifetimes — the vertex shader shows a point only while `birth_time <= t < removal_time` against a per-cloud scrub-time uniform (culled points get `gl_Position` shoved outside the clip volume: clipped pre-raster, zero fragment cost — Potree's GPS-time-filter trick, patched into the stock `PointsMaterial` via `onBeforeCompile` + a `customProgramCacheKey` per attribute combination). This expresses **out-of-order** appearance/removal that `draw_range`'s buffer-prefix reveal cannot (issue #79: material removal isn't a prefix). NaN/±inf ends mean unbounded (NaN birth = always existed, NaN removal = never removed; Python maps them to ±FLT_MAX because GLSL NaN compares are undefined). The scrub time starts at 0 and is driven by `set_points_time(id, t)` (streaming; validates finite, no-ops on objects without a window) or the `point_times` animation channel (`Animation.set_point_time_data` / `Frame(point_times={...})`) so the animation slider scrubs points in/out; the uniform object is shared by reference into every program compiled from the material (incl. the EDL depth pre-pass), so scrubbing touches no material state. `unload_animation` leaves the scrub time untouched (there is no universal "all visible" time once birth and removal both exist). **Octree LOD** (`add_points(..., lod=True)` or a dict of `node_capacity`/`point_budget`/`refine_pixels`/`max_depth`/`seed`; design + prior-art rationale in `plans/points-octree-lod.md`): for clouds beyond the flat tier, Python builds a Potree-style **additive sampled octree** (`points_lod.py` — every node owns a seeded pseudo-random sample of its cube, **time-stratified** over birth/removal times so the time filter thins every LOD level uniformly; children add detail, no point stored twice; per-node sample vertex order is Morton-sorted then shuffled in 128-point batches for raster throughput). The cloud is reordered so each node is a contiguous slice; the browser gets one `add_points_lod` WS message + a 40 B/node binary hierarchy blob (bounds, count, `[min birth, max removal)` time bounds, BFS `first_child`/`child_mask` topology), and **node payloads stream on demand**: per-frame priority traversal (`_updatePointsLOD`, max-heap on projected node size) refines while a node projects ≥ `refine_pixels` and stops adding at `point_budget` (default 1.5M); missing wanted nodes are fetched (≤6 concurrent) from lazy **callable blob-store providers** that quantize + pack a numpy slice per request (`GET <sidecar>/points_lod_<uuid>/<i>`), and loaded-but-unwanted nodes LRU-evict past ~3× budget. Node payload: **normalized int16 xyz** over the node cube (dequantized free via normalized attributes + the node `Points`' center/scale transform — ints stay GPU-resident, unlike Potree's CPU float decode) + u8 rgb + f32 birth/removal (u16 time quantization deferred: needs an immortal-flag sentinel). **Grid fast-path**: for lattice-aligned clouds (voxel centres) pass `lod={"grid": {"spacing": pitch}}` — `build_points_octree_grid` builds the same octree via one global uint64 Morton code + one sort (every octree cell at every level is then a contiguous range; octants split by `searchsorted`, no per-node re-partition), ~4× faster than the float builder and flat in N (8M ≈ 1.1s vs 4.4s). Result is structurally identical; sampling is a plain strided (spatial) subsample — `strat_times` accepted but ignored, because carve removal times are spatially correlated so a spatial sample stays honest under the scrub, and skipping the time sort keeps the build reproducible for external producers. An external producer (mill-sim's Rust kernel) can pre-supply `"codes"`/`"order"`/`"n_bits"` (global Morton codes + their sort permutation) and the builder skips its two super-linear stages; the bit-exact contract lives in `docs/points-lod-grid-api.md` with `grid_morton_codes()` as the Python reference. Only declare `grid` for genuinely lattice-aligned clouds — the bit-slice octant test matches the float `pos > centre` test exactly only for cell-centred points. `lod={"size_boost_max": k}` (default 2.0, `>= 1.0`, 1.0 = off) caps the coarse-node point-size fattening per cloud; the header field is `sizeBoostMax`. **Runtime tuning**: `set_points_lod_options(id, point_budget=, refine_pixels=, size_boost_max=)` re-tunes a streamed cloud live with no re-upload or octree rebuild (issue #87 — the traversal reads these fresh every frame; a `size_boost_max` change also re-derives the point size on already-streamed node materials via the shared `lodNodeSize(lod, i)` free function). Fields left `None` are unchanged; values are transient viewer state like `set_camera` (a browser refresh reverts to the add-time `lod=` options). Per-node explicit bounding sphere/box (frustum culling per node); nodes whose time bounds miss the scrub time are skipped for draw *and* fetch (scrubbing to a dead region costs nothing) but still descended. Coarse nodes draw slightly fatter points (√2/level, capped 2× — aggressive boosts turn coarse ancestors into giant occluding sprites near the camera). The group carries the shared `userData.timeUniform`, so `set_points_time`/`point_times` address a LOD cloud identically to a flat one. Caveats: **the Python process must stay alive to serve refinement** (loaded nodes survive, deeper zoom won't sharpen without the server); `set_draw_range`/`draw_ranges` are no-ops on LOD clouds (buffer order is per-node Morton — use the time window); picking not wired; client-side state is released on `delete`/`clear`/re-add (`_release_points_lod`).
- 3D models: GLTF/GLB, STL, OBJ, FBX, DAE, PLY, 3DS
- **draw_range**: polylines, meshes, parametric tubes, *flat* point clouds, and swept tool bodies support `set_draw_range(id, 0.0-1.0)` to control visible fraction, and `draw_ranges` channel in animation frames. Two LOD systems differ here on purpose: **tube LOD keeps draw_range** (the viewer remaps the fraction onto the reduced geometry by arc length, `remapDrawRangeToReducedPairs`), while **octree-LOD point clouds (`add_points(lod=...)`) do not** — their buffer is per-node Morton order, so a leading-fraction prefix is spatially meaningless; drive per-point visibility with the birth/removal **time window** instead (which is also the only mechanism that can express out-of-order removal). The viewer warns once per LOD cloud if a draw_range is sent at it. One `draw_ranges` channel can drive **multiple objects of different types in lockstep** — `set_draw_range_data([tube_id, line_id, cloud_id], data)` dispatches per `userData` type per object, so heterogeneous reveals (bead + travel line + point cloud) stay on one clock.
- **Polyline / tube picking**: opt-in interactive picking of a point *along* any polyline **or parametric tube** (the "bead"), owned by the in-file `PolylinePickController`. Enable from Python with `enable_polyline_picking(marker_color=..., threshold_px=...)` or `on_polyline_pick(callback)` (the latter also enables it). When on, hovering near a pickable object glides a screen-constant marker to the closest point on its spine and shows a cursor readout of the arc-length fraction; a click (not a drag) sends `{id, kind, fraction, point, local_point, segment, t}` back over the WebSocket, where it is dispatched to registered callbacks. `kind` is `"line"` or `"tube"`; `fraction` is the headline value (position in `[0,1]` along total arc length). **Movement is continuous — the marker never snaps to vertices.** Picking is a two-stage hit test (fat `Line2`, native `THREE.Line`, and tubes treated identically): (1) **select** the nearest spine segment by 2D screen distance (nodes projected to pixels) — choosing in 2D means segment *i* ends where *i+1* begins at a shared node, so the hand-off is seamless; (2) **place** the point on that segment via the 3D ray↔segment closest-point (`Ray.distanceSqToSegment`), because a screen-space parameter foreshortens under perspective and would quantize the marker toward the nearer endpoint. The per-object gate is `threshold_px + halfLineWidth` for a line, or `threshold_px + beadHalfExtentPx` for a tube (the bead's half cross-section, projected to pixels per node via the node's view-space depth, so a click anywhere on the bead body — not just its centre-line — registers; the resolved point still sits on the spine). The fraction is read off a retained CPU copy of the local spine points (`userData.pickPoints`) + a lazily-built cumulative arc-length table, so it's exact regardless of the raycaster's reported hit. **For a tube, `pickPoints` is the full-resolution spine (1:1 with the per-spine-point arrays passed to `add_parametric_tube`, independent of LOD), so `segment` is a direct index into the caller's per-point data dimensions** — the basis for looking up other dimensions at the picked point. The trade-off of screen-space selection is no depth ordering between overlapping objects (screen-nearest wins; picking already ignored mesh occlusion). Picking is **opt-out per object**: `add_polyline`/`add_parametric_tube` default `pickable=True`; `pickable=False` drops that object from the pick loop (still rendered, never a target). Picking is inert (zero per-hover raycast cost) until enabled, and **costs nothing at object-add time when never used** — the loaders only stash references to arrays already held (`pickPoints` = the line's point buffer or the tube's full-res spine; plus the tube width/height arrays), and a tube's per-node bead half-extents are built lazily on the *first* pick (`_ensureTubeHalfExtents`), not at load. Picking state is re-sent on browser reconnect. The marker lives in the scene like the pivot marker (not in `_objects`) so it can't be picked and survives `clear`. `disable_polyline_picking()` turns it off. **Client-side hooks**: a browser embedder can drive picking without a Python round-trip via `viewer.enablePolylinePicking(opts)` / `viewer.onPolylinePick(cb)` (click) / `viewer.onPolylineHover(cb)` (every hover move, payload or `null` on leave) / `viewer.disablePolylinePicking()`. The hook payload is a plain `{id, kind, fraction, segment, t, point:{x,y,z}, localPoint:{x,y,z}}`; registering a hook auto-enables picking, and each `on*` call returns an unsubscribe function. Picks fire both the JS hooks and the WebSocket send when connected.
- **Wireframe display**: press `M` to cycle scene display modes globally: normal → wireframe-only → combined (solid + black wireframe overlay) → normal. Purely a viewer-side toggle; no Python API.
- **Shading debug**: press `N` to cycle shading debug modes globally: off → normals-as-color (`MeshNormalMaterial` swap) → UV checker (procedural checkerboard with red U / green V axis bands) → vertex-normals helper (cyan line segments per vertex). Independent of `M` — they compose (wireframe overlays draw on top of swapped materials). Viewer-side toggle; no Python API.
- **Line depth cues**: depth-perception aids for flat line drawings (the `add_polyline` fallback for toolpaths too complex to extrude as shaded beads). Two composable cues, owned by the in-file `DepthCueController`. Press `D` to toggle **distance fog** (CAD depth cueing, far lines dim toward near-black via `THREE.Fog` whose near/far are fitted each frame to the closest→furthest view-space depth of the visible lines — `_updateFogRange()` aggregates the per-polyline bounding-box corners in view-Z and anchors `near` to the closest line, but pushes `far` past the furthest so the content spans only `FOG_DEPTH_COVERAGE` (≈0.4) of the white→fog ramp — mapping it into the smoothstep toe so the bulk of the lines stay near the light end (~70% under 0.2 fog) and darkening concentrates on the farthest stretch (furthest ≈0.35). Far lines stay partially lit instead of crushing to fog colour, and the cue tracks the actual content rather than the looser whole-scene sphere. Falls back to the scene-sphere proxy when no line geometry is visible). Press `Shift+D` to toggle **eye-dome lighting** — a screen-space EDL post-process that darkens fragments sitting behind their screen-space neighbours, sculpting line bundles into legible 3D. The two compose (fog dims globally, EDL adds local crossing contrast); a bottom-centre toast names the active state. Also drivable from Python via `set_depth_cue(fog=None, edl=None, edl_strength=None, edl_radius=None)` (each bool toggles its cue; `None` leaves it unchanged; strength/radius re-tune the EDL shader live — stored on the controller so they survive composer rebuilds and can be set before the composer exists) so a script can open straight into fog + EDL, plus a focused `set_edl(enabled=True, strength=None, radius=None)` (new `set_edl` message). **EDL auto-enables the first time a point cloud is added** (flat/LOD both — unlit point quads read as a washed-out sheet without a depth cue); the auto-enable is suppressed once the user *pins* the EDL state (`Shift+D`, `set_depth_cue(edl=...)`, or `set_edl(...)` — `_edlUserSet`), including an explicit OFF, so `set_edl(False)` sticks even for point clouds. EDL lazily builds an `EffectComposer` (`RenderPass` → EDL `ShaderPass` → `OutputPass`) with a shared `DepthTexture` on `renderTarget2` only (attaching it to `renderTarget1` too forms a GL feedback loop). `OutputPass` re-applies tone mapping/sRGB since the scene renders linear into the float target. **`OutputPass` would also tone-map the solid background** (crushing `#222222`→`#101010` under ACES, so EDL-on visibly darkened the viewport vs the direct render), so `renderComposer()` renders the background transparent (`scene.background = null` around the whole composer pass, pre-pass included — a `Color` background's `setClear(color, 1)` GL state persists and would leak an opaque clear into `RenderPass`); the renderer is created with `alpha: true`, the canvas CSS `background-color` is set to the same `#222222` to show through, and the final `OutputPass` is set to `NoBlending` so it *replaces* every canvas pixel (transparent for background, no trails). **Fog does not survive the composer's `RenderPass`**, so the EDL shader re-applies linear fog from depth (`fogMode`/`fogColor`/`fogNear`/`fogFar` uniforms driven from `scene.fog`) — otherwise fog washes out entirely under the EDL overlay. **Both cues are scoped to polyline geometry only** — meshes (cell/fixtures/shaded beads/models) render exactly as with the cues off, so they stay a clean spatial reference. Fog: `scene.fog` is global and every material defaults to `fog:true`, so `_applyFogScope()` force-disables fog on non-polyline materials (saving the prior value on `material.userData._fogScopeSaved` to restore on toggle-off) and enables it only on polylines; it re-runs from `update()` whenever `_objGeneration` changes so objects added while fog is active (incl. async model loads) are scoped too, and also when the `M`/`N` shading-debug toggles change mode (those swap in a debug material or add a wireframe-overlay child without bumping `_objGeneration`, and would otherwise dim under fog). EDL: polylines are placed on a dedicated camera layer (`EDL_LINE_LAYER = 1`, in addition to layer 0) and `renderComposer()` runs a **line-only depth pre-pass** (`camera.layers.set(EDL_LINE_LAYER)` → render into `_lineDepthTarget`) that feeds the EDL pass's `tDepth`; the shader early-outs where line-only depth is far (every non-line pixel), and an occlusion guard against full-scene depth (`tSceneDepth`, the composer's `renderTarget2.depthTexture`) leaves a mesh that sits in front of a line untouched.
- **Clipping plane**: interactive cross-section plane with GUI panel (press C to toggle). Supports single plane and slab (dual-plane) modes. Two gizmos ride the same `_clipAnchor`, both wearing the **refined gizmo styling** shared with the move/rotate gizmo: a **rotate** gizmo (`_clipGizmo`, slimmed to the three coloured rings) for orienting the plane normal, and a **normal-slide** gizmo (`_clipMoveGizmo`, a local-space, Z-only/`showX=showY=false` translate handle with a shaded cone) for dragging the plane along its current normal (arrow keys / the position slider still nudge it too). Both report through one `_syncClipFromGizmo` handler (normal from the anchor orientation, distance from `position·normal`) and are enabled/hidden together with the panel. The refined look comes from the in-file free functions **`refineGizmoHandles(control)`** (one-time: strip the bulky `E`/`XYZE`/`AXIS` rotate handles, swap translate cones to lit `MeshStandardMaterial`) and **`restyleGizmoHelper(helper, sizedPlanes)`** (per-frame re-theme to the palette; `TransformGizmoController._refineHandles`/`_restyleGizmo` are now thin wrappers over these, so the move gizmo and the clip gizmos can't drift). The clip gizmos are restyled each frame from `_animate` while `_clipGizmo.enabled`. V key snaps ortho camera to clip normal for slice inspection. Programmatic control via `set_clipping_plane(normal, distance, show_helper)` / `set_clipping_slab(normal, center, thickness, show_helper)` / `disable_clipping_plane()` / `set_clipping_defaults(normal, distance)`
- **Lighting panel**: runtime tone-mapping / exposure / environment-map (on/off) / environment-intensity / ambient-intensity controls (press `E` to toggle). Tone-mapping modes: `none`, `linear`, `reinhard`, `cineon`, `aces` (default), `agx`, `neutral` — switching modes flushes every material's shader (`material.needsUpdate = true`) because three.js bakes the tone-mapping constant into compiled programs. **Environment-map toggle** (uglier-but-faster perf knob): a checkbox that nulls `scene.environment` — dropping the per-pixel PBR IBL reflection lookups for a flatter but faster render — and restores the retained PMREM map (`_envMap`, kept off the scene while disabled so there's no rebuild) when re-checked; the env-intensity slider disables while the map is off. Panel values persist in `localStorage` under the `tjsv.` namespace (env-map as `tjsv.environmentMap` = `"true"`/`"false"`); Reset clears those keys and restores the page-load baseline. Initial values resolve as **URL query param > `ThreeJSViewer` option > localStorage > hard default** (Reset ignores localStorage so it actually escapes persisted tweaks). Programmatic control from Python via `ViewerClient(tone_mapping=..., tone_mapping_exposure=..., environment_intensity=..., environment_map=True|False, ambient_intensity=...)` — these are forwarded as query params on the viewer URL (`environment_map` as `environment_map=true|false`, parsed by a `parseBool` that also accepts `1`/`0`/`on`/`off`/`yes`/`no`) and act as authoritative initial values that win over localStorage on reload. Invalid `tone_mapping` in Python raises `ValueError`; invalid values from URL/localStorage in the browser silently fall through to the next level.
- **Camera FOV**: the perspective camera's vertical field-of-view (degrees) defaults to **40°** (a flat, CAD-ish look — was 75°) and is configurable via the `fov` `ThreeJSViewer` option, the `fov` URL query param (wins over the option), or the `ViewerClient(fov=...)` Python kwarg (forwarded as that query param). Precedence: **URL param > option > 40° default** — no localStorage/panel layer. The browser clamps to `[1, 179]°` (out-of-range incl. ±Infinity clamps; NaN/empty fall through — a stray value degrades, never throws); the Python kwarg validates eagerly and raises `ValueError` for non-finite or out-of-`(0, 180)` values. Resolved by `resolveFov()` into `this._fov`, consumed once in `_initThreeJS`; all world↔pixel math reads `camera.fov` live so it follows automatically. There is no runtime setter (no in-viewer FOV control). (`set_camera(fov=...)` below is the runtime override.)
- **Camera pose API**: `get_camera()` / `set_camera(position=, target=, up=, fov=, zoom=)` — read/write the live camera pose over the socket. `get_camera()` is a request/response round-trip (requestId like `query_scene`) returning `{position, target, up, fov, zoom}` (`fov` is `None` while ortho is active; `zoom` is the framing control for ortho). `set_camera` applies only the provided fields, clamps `fov` to `[1, 179]`, and **explicitly re-orients via `camera.lookAt(target)`** — `ViewerControls.update()` deliberately never calls lookAt, so without it a position/target change would move the camera while it kept facing its old direction. Python validates eagerly (3-vectors, finite, `fov` in `(0, 180)`, `zoom > 0`). Intended workflow: orbit to a view by hand, `get_camera()`, paste into `set_camera(...)` to pin a scripted default. Pose is transient (not replayed on reconnect). Related: `frame_object(id)` fits the camera to one object (programmatic double-click).
- **Move/rotate gizmo**: opt-in interactive transform manipulator, owned by the in-file `TransformGizmoController`, which wraps three.js `TransformControls` (reusing its drag/rotate/snap math) rather than hand-rolling a gizmo. The controller manages a `_primary` interactive gizmo (the click-select / `enable({id})` target, always present so the legacy `control`/`helper`/`object`/`objectId` surface keeps working as getters) **plus any number of pinned `_extra` gizmos** (`add_gizmo`), each its own `TransformControls` with its own axis constraint and base mode but all sharing the controller's modifier handling, snap settings, drag ghost, and report/change hooks. Per-target state (object, id, axes, ghost, snap origin, sized-plane set) lives on a small in-file `Gizmo` record. Enable from Python with `enable_move_gizmo(id=None, mode="translate", translate_snap=1.0, translate_snap_relative=False, rotate_snap_deg=15.0, click_select=True)` / `on_object_move(callback)`, or from JS via `viewer.enableMoveGizmo` / `viewer.attachMoveGizmo(object3D, id=null)` / `onObjectMove` / `onObjectChange` / `setGizmoMode` / `setGizmoAxes` / `setGizmoTranslateSnap` / `disableMoveGizmo`. Held **Alt** = rotate (locked at drag-start), held **Shift** = snap (translate grid / rotate degrees, sampled live) — but **Shift toggles snap relative to the gizmo's resting state**: a normal gizmo is free at rest so Shift *enables* snap, whereas a `snapDefault` gizmo snaps at rest so Shift *releases* it for free placement (same key, inverted; Shift dodges the macOS Ctrl-click-is-right-click trap). `_syncModifiers` computes `g.snapDefault ? !shiftKey : shiftKey` per gizmo and `_onDragChange` re-applies the resting snap at drag-start from the live step + last-seen Shift state (`this._shiftHeld`), so a `snapDefault` gizmo snaps from the first drag even with no key pressed and even if the snap step was set after the gizmo was pinned. Alt is a *momentary* override: it switches the live control to rotate while held and falls back to the caller-set base `mode` on release (it does not mutate `this.mode`), so an Alt tap can't clobber a `setGizmoMode('rotate')`. Target selection is both: `id=` attaches immediately, and `click_select` (default on) attaches by clicking any object (whole-object raycast; a drag is an orbit, not a select). **`viewer.attachMoveGizmo(object3D, id=null)`** is the JS-only escape hatch for an embedder: it attaches the gizmo to *any* `Object3D` (including a bare sentinel the viewer never tracked in `_objects`, which `enableMoveGizmo({id})` can't reach) and auto-enables the controller (modifiers, per-frame update loop, and move reporting all go live). The internal `attach()` ensures-enabled via a shared `_activate()` so a programmatic attach behaves like an interactive one. **Axis constraint**: `set_gizmo_axes(x=True, y=True, z=True)` (Python) / `viewer.setGizmoAxes({x,y,z}|null)` (JS) hides individual translate arrows / rotate rings (e.g. `{x:false,y:false,z:true}` for a Z-only rail) by driving `TransformControls.showX/Y/Z`; an axis is shown unless its key is explicitly `false` (omitted/`null` → all shown). It's additive (`_restyleGizmo()` never touches `showX/Y/Z`) and the primary's `detach()` resets to all-axes, so a constraint set for one target doesn't silently leak to the next attach — the Python state is re-sent on reconnect *after* the enable, and cleared on `disable_move_gizmo`. `set_gizmo_axes` targets the interactive gizmo; pinned gizmos get their constraint at `add_gizmo` time. **Multiple gizmos**: `add_gizmo(id, x=True, y=True, z=True, mode="translate", space="world", snap_default=False)` (Python) / `viewer.addGizmo(objectOrId, {axes, mode, id, space, snapDefault})` / `viewer.clearGizmos()` (JS) pins a *persistent* gizmo to an object, one per call, so several objects can each carry their own manipulator at once — the axis flags are the same `setGizmoAxes` semantics, so `x=False,y=False,z=True` is a 1-DOF rail, `x=True,y=True,z=False` is a 2-DOF in-plane slider (two arrows + the XY plane chip), and all-true is the full 3-DOF gizmo. `space` (validated against `_ALLOWED_GIZMO_SPACES` in Python) drives `TransformControls.setSpace`: `"world"` (default) keeps the handles world-axis-aligned, `"local"` orients them to the object's own rotation so the gizmo turns with a tilted object. `snap_default=True` flips the snap convention for that gizmo (snap is the resting state, Shift moves freely — see the modifier note above); the snap *step* still comes from the interactive gizmo's `translate_snap`/`rotate_snap_deg`, and `snap_default` is also accepted on `enable_move_gizmo`. See `examples/24_gizmo_dimensions.py`, which pins a world row and a rotated local row, all `snap_default=True`. Pinned gizmos report through the same `on_object_move` callback, are re-pinned on reconnect (each `add_gizmo` message re-`_activate()`s the subsystem, so no separate enable is needed), and are dropped by `clear_gizmos`, `disable_move_gizmo`, or a scene `clear` (the per-frame `update()` also prunes any whose target object left the scene). `on_object_move` only auto-enables the click-select interactive gizmo when **no** gizmo is configured (neither the interactive one nor any pinned one), so pinning then registering a callback doesn't draw an extra interactive gizmo. **Drag ghost**: on `dragging-changed` the controller drops a translucent clone (`__gizmoGhost`, opacity `GIZMO_GHOST_OPACITY`) of the dragged object at its grab-time world pose, parented to the scene root (so it stays put while the object moves), and removes + disposes it on release — the clone shares the source geometry but gets its own faint, depth-write-free materials and never raycasts. **Relative translation snap**: `enable_move_gizmo(translate_snap_relative=True)` / `enableMoveGizmo({translateSnapRelative:true})` / `viewer.setGizmoTranslateSnap(step, {relative:true})` quantises the drag *delta* from the grab-time position (captured on `dragging-changed`) instead of an absolute world grid — an item at `347` nudged a step lands at `447`, not on the nearest grid line. In relative mode the native (Shift-held) absolute `translationSnap` is suppressed and the quantise runs by hand inside `_onObjectChange` on **every** drag frame (always-on, not Shift-gated; only in translate mode); `setGizmoTranslateSnap(null)` disables snap entirely, and `{relative:false}` restores absolute grid snap. Rotation snap stays Shift-gated. **Per-frame change hook**: `viewer.onObjectChange(cb)` fires synchronously on every `objectChange` (each rendered drag frame, before the throttled report), payload `{object3D, id}`; the hook may mutate `object3D.position`/`.quaternion` and the change is reflected in the subsequent report. Ordering inside `_onObjectChange` is **relative-snap → change hooks → `_report`**, so both a hook and the report observe the snapped pose. Use it for live numeric readouts (the 30 Hz report is visibly jittery) without a WS round-trip; returns an unsubscribe fn. Drags report `{id, position, quaternion, scale, matrix, positionStart, quaternionStart, mode, phase}` back to `on_object_move` (throttled `"move"` ≤30 Hz + final `"end"`); `positionStart`/`quaternionStart` (Python: `position_start`/`quaternion_start`) carry the grab-time pose captured on drag-start, so a consumer can reconstruct the original world matrix from the payload, and `mode` is the **effective** mode of the drag read off the live control (`"translate"`/`"rotate"`/`"scale"`) — during an Alt momentary rotate override it reports `"rotate"` while the base mode stays translate, so consumers that branch translate-vs-rotate must use this field, not the mode they configured (issue #84: without it, Alt rotate-drags were silently discarded by embedders). Enabled state replays on reconnect. Orbit is suppressed during a handle drag via `dragging-changed` (like the clip gizmo); the gizmo follows the active camera across persp↔ortho switches (`control.camera` synced each frame) and lives in the scene (not `_objects`) so it survives `clear` and auto-detaches if its target is deleted. **Restyle**: `_restyleGizmo(g)` runs per gizmo every frame. `TransformControls` re-themes its handles every frame from a cached `material._color`/`_opacity`, so the controller overwrites that cache each frame for a refined palette (colours cached per hex to avoid per-frame allocation); geometry tweaks persist because the lib bakes each handle's offset into its geometry at setup (`applyMatrix4`) and thereafter only re-*transforms* handles (sets `handle.position = worldPosition`, scale-to-screen). Translate plane chips are enlarged about their own centroid **and pushed outward by `GIZMO_PLANE_MARGIN`** along their offset direction (so the three chips leave a gap around the gizmo centre instead of crowding the origin) — applied to the visible chip *and* its invisible picker both, so the hit area tracks the visual. Each chip is also **flattened to a quad**: the stock chip is a thin `BoxGeometry` (depth `0.01`), which reads as a 3D slab and whose edge outline draws a back rectangle too — so the resize collapses the chip's thinnest bbox axis (detected, not hardcoded, because the box is pre-rotated/baked) to zero. A bright edge outline is added as a child of the **visible** chip only: the picker discriminator is the parent group's visibility (`o.parent.visible === false`), **not** the material's `visible` flag — `matInvisible` is opacity-based (`visible:true`), so a stale `m.visible === false` test let outlines leak onto picker chips, and a raycastable outline on a picker is hit before the chip and reports an empty `axis`, silently breaking plane-chip dragging. Both `_restyleGizmo(g)` and `_refineHandles(g)` are thin wrappers over the in-file free functions `restyleGizmoHelper(helper, sizedPlanes)` / `refineGizmoHandles(control)`, which the clipping tool's two gizmos reuse for the same refined look (see the Clipping plane entry). **`_refineHandles(g)`** is a separate *one-time* structural pass (per gizmo, at construction — distinct from the per-frame `_restyleGizmo`): (1) it slims the rotate gizmo to just the three coloured axis rings by removing the bulky outer screen-space ring (`E`), the gray full-circle backdrop (`XYZE`), and the gray `AXIS` helper line from the rotate gizmo/picker/helper groups; (2) it swaps each translate arrow's flat unlit `MeshBasicMaterial` for a lit `MeshStandardMaterial` (axis colour, small emissive floor, `depthTest/Write:false`, `toneMapped:false`) so scene lighting/environment give the cones real depth — the lib's per-frame re-theme/highlight only touch `.color`/`.opacity`, which `MeshStandardMaterial` supports, so they keep working. No runtime UI/keys of its own (distinct from the clip gizmo's `C` panel).

### Animation: Two Approaches
**Frame-based (simple, familiar):** Build frames as Python dicts — good for small animations and prototyping.
**Binary channels (fast):** Use `add_channel()` / convenience wrappers for large animations (100+ objects × 1000+ frames). Data is packed as typed arrays, transferred via HTTP, and applied with zero-copy TypedArray views in JS.

Binary channel API:
- `animation.set_frame_times(times)` — numpy array of frame times
- `animation.set_transform_data(object_ids, data)` — (n_frames, n_objects, 16) float32
- `animation.set_draw_range_data(object_ids, data)` — (n_frames, n_objects) float32
- `animation.set_clip_time_data(object_ids, data)` — (n_frames, n_objects) float32
- `animation.set_point_time_data(object_ids, data)` — (n_frames, n_objects) float32 point-cloud scrub times
- `animation.add_channel(name, ids, data, dtype, stride, metadata)` — generic channel

Supported channel types: `transforms` (stride=16), `draw_ranges`, `colors`, `visibility`, `opacity`, `clip_times`, `point_times`
Supported dtypes: `float64`, `float32`, `uint32`, `uint8`. The `draw_ranges`, `clip_times`, and `point_times` convenience setters pack **float64**: their values are fractions of total arc length / absolute seconds, where one float32 ulp is ~0.5 mm of frontier position on a multi-km toolpath or ~16 ms at t=160,000 s (knots wobble, ms-spaced keys collapse to equal values). `transforms` and camera channels stay float32 (mm-scale values, and 2x the bytes would be real memory there). The packer sorts channels by element size descending so the float64 block leads the payload and every channel's byte offset is aligned to its element size; the viewer copies misaligned hand-packed `handleMessage` payloads instead of throwing.
Indexed colors: `dtype="uint8"` + `metadata={"colormap": [0x44AA44, 0xFF3333]}`

Binary channels and Frame-based JSON can coexist. A binary channel supersedes the same-named Frame field.

**Interpolation (per-channel):** Every *binary* animation channel carries its own interpolation mode — `"linear"` (lerp/slerp between keyframes) or `"hold"` (keep the previous keyframe's value until the next one hits). **Every channel defaults to `"linear"`** — opt out per channel with `add_channel(interpolation="hold")` or via the convenience setters (`set_transform_data`, `set_draw_range_data`, `set_clip_time_data`, `set_point_time_data`, `set_camera_target`, `set_camera_position`). Translations lerp, rotations slerp, float channels lerp element-wise, and `colors` lerps hex values in 8-bit RGB space (works for direct hex and colormap-indexed `uint8`). The `visibility` channel is a boolean and always left-holds regardless of the setting — a "linear bool" has no meaningful interpretation; the setting is accepted and validated but has no effect on that channel. **JSON `Frame` objects do not carry interpolation metadata and always interpolate linearly** between consecutive frames (visibility aside) — if you need hold behavior, use a binary channel. There is no Animation-wide knob — it was redundant with per-channel. Linear playback lets producers sample at the signal's bandwidth (e.g. 10 Hz) and still get smooth 60 fps. See `examples/17_animation_interpolation.py` for a HOLD ⇄ LINEAR comparison on the same tumbling capsules.

- `24_gizmo_dimensions.py` - Six gizmos pinned at once via `add_gizmo`, in a 2×3 grid: columns are 1-DOF / 2-DOF / 3-DOF (a blue Z-only rail `x=False,y=False,z=True`, a green XY-plane slider `x=True,y=True,z=False`, an orange free cube), rows are orientation space — a back row of upright blocks with `space="world"` (world-aligned handles) and a front row of *rotated* blocks with `space="local"` (the gizmo turns with the tilted object). Shows the persistent multi-gizmo API, the per-axis DOF mapping, world-vs-local space, the translucent drag ghost, the flat margined plane chips, and the shaded cones / slimmed rotate rings; releases report through one shared `on_object_move`.
- `25_point_cloud.py` - GPU point cloud via `add_points`: a dense (~160k-point) machined "cut surface" sampled along a serpentine raster and coloured by signed deviation (turbo heatmap) with `size_attenuation`. A `draw_ranges` animation sweeps the buffer to reveal points along the toolpath like a material-removal pass; notes the cloud stays one draw call so `side` can be bumped toward millions of points.
- `26_swept_tool.py` - 5-axis swept tool body via `add_swept_tool`: a tilting ball+shank tool lofted along a contact path, coloured by reorientation rate (blue calm → red fast wrist motion) packed per-station, with a `draw_ranges` animation advancing the tool along the path. Shows the tool-axis-decoupled-from-path-tangent sweep, the `(height, radius)` profile, and per-station heatmap colouring.
- `27_points_octree_lod.py` - Octree LOD + per-point time windows on one abstract cloud (issue #79), point count tunable via argv (default 2M): a wavy sheet with `lod=True` streams node detail on demand under the point budget as you zoom, while a diagonal build front (`birth_times`) adds points and a trailing erosion front (`removal_times`) removes them out of buffer order — drag the animation slider (a `point_times` channel maps the playhead 1:1 onto the scrub time); a NaN-removal "bedrock" band persists forever.
