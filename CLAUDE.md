```bash

uv run python src/threejs_viewer/viewer/build.py  # regenerate viewer.html with substituted version
```

The placeholder appears in three files: `pyproject.toml`, `src/threejs_viewer/__init__.py`, `src/threejs_viewer/viewer/viewer.js`. The build step propagates the version into `viewer.html`. Never commit a real version number — always keep `0.0.0-dev`.

## Project Overview

A lightweight Three.js viewer designed to be controlled from Python/Jupyter notebooks. Primary use case: visualizing 3D data and animations at 60fps. The browser viewer persists across Python script restarts.

## Architecture

### Tech Stack
- **Viewer**: Static HTML/JS (no build tools, no Node, no frameworks)
- **Three.js**: Loaded from CDN (unpkg)
- **Python**: WebSocket server via `websockets` library

### Communication Model
- **Direct connection**: Python runs WebSocket server on port 5666 (default), browser connects to it. Port is overridable via `?ws_port=` query param in viewer URL.
- **Browser survives restarts**: Viewer auto-reconnects when Python script restarts
- **Binary transfer**: Large data (models, polylines, animations) served via HTTP sidecar on port 5667, browser fetches with native `fetch()`. **HTTP status guard** (issue #142): every sidecar/blob fetch in the message handler goes through the free function `fetchArrayBuffer(url, what)`, which throws a descriptive Error on non-2xx (message type + object id + status + url) — so a 404/expired blob logs one clear console.error and skips cleanly (add-object cases also reject their inflight deferred) instead of handing the error body to a binary parser/model loader, which failed deep inside with an uncaught `RangeError: Invalid typed array length` and a silently missing object. The sidecar's 404 response carries the CORS header too, otherwise a `file://` viewer page sees an opaque CORS failure instead of the real status. The only bare `fetch` left in viewer.js is the no-cors WS-port reachability probe (opaque response — `resp.ok` is meaningless there). **Superseded-fetch quieting** (issue #157): a delete or a re-push of the same id while its blob fetch is still in flight is *expected* traffic — the producer drops the old blob as it sends the delete, so the in-flight fetch 404s — and #142's guard turned that into a loud console.error. Two halves. (1) **Cancellation**: every blob fetch is registered per id in `_loadAborts` (`_trackFetch(id, {supersede})` / `_untrackFetch` / `_abortFetches`) and gets an `AbortSignal` (`fetchArrayBuffer(url, what, signal)`); `_deleteObject` (hence `delete`, `clear`, and any non-binary re-add) aborts the id's fetches, and every binary *add* case supersedes — aborts the previous fetch for that id — before registering its own. Read-side fetches (`update_polyline_colors`, `update_parametric_tube_colors`, `set_follow_path`, the octree-LOD node stream) register **without** superseding so they can't cancel a concurrent add, but still cancel with the object. When the delete wins the race, no request is left open, so the 404 is never even issued. (2) **Classification**: every binary-load catch now goes through `_reportLoadFailure(err, what, loud, ctx)`, which logs one quiet `Discarding superseded <what> fetch for '<id>'` when `_isLoadSuperseded` holds (an `AbortError`, or a bumped `_sceneGeneration`/`_animGeneration`/load token) and otherwise runs `loud` — the unchanged, fully-attributed console.error of #142/#146. Because the 404 (HTTP) can arrive *before* the delete/re-add that explains it (WebSocket — separate transports), a **fetch-stage** failure that still looks live is re-checked after `SUPERSEDED_FETCH_GRACE_MS` (500 ms, test seam `window.__supersededFetchGraceMs`) before it shouts; post-fetch (parse) failures report immediately, and the load token is only consulted for the fetch stage since installing an object bumps its own token. Net: a 404 for a **live** object is still a loud error (unchanged #142 behaviour, ~500 ms later); a 404 for a deleted/re-pushed one is one quiet log line.
- **Batch updates**: `batch_update()` updates multiple objects in one message
- **60fps capable**: Minimal JSON payloads with 4x4 matrices
- **Embedder camera/pick/controls API** (issue #77): `viewer.getCameraPose()` → `{position, target, up, fov, zoom}` (`fov` null under ortho); `viewer.setCameraPose({position, target, up, fov, zoom})` — one-shot partial pose set, vectors accept `{x,y,z}` or `[x,y,z]`, explicitly `lookAt`s the target (ViewerControls never re-orients itself) and is also the implementation behind the `set_camera` WS case so the two can't drift; `viewer.frameBox(min, max, margin=1.5)` — fit the camera to a world AABB (`frameObject` for a box); `viewer.pick(clientX, clientY, {pointsThreshold, ids})` — raycast **meshes + point clouds** (lines excluded on purpose — `enablePolylinePicking` is the arc-length-aware path) from viewport coords, skips hidden subtrees, resolves the **top-level tracked id** by walking ancestors (a GLTF sub-mesh reports its model's id), returns `{point, objectId, distance, object3D}` of the nearest hit or `null`; `viewer.setControlsEnabled(bool)` — suppress orbiting while an embedder drags its own handle. All JS-only (no Python/WS surface beyond the existing `get_camera`/`set_camera`).
- **Embedder animation/object/overlay/status API** (issues #74/#75/#76/#78): `viewer.seekAnimationTime(s)` / `getAnimationState()` → `{time, duration, playing, speed, loop}` (null when no animation) / `setAnimationPlaying(bool)` / `setAnimationSpeed(mult)` (parks the native ± stepper on the nearest predefined step) / `onAnimationTime(cb)` (fired with the full state on every applied frame — playback tick, seek, frame step — and on play/pause flips; returns an unsubscribe fn; saves embedders a rAF poll) — all around the **one shared clock** that also drives draw_range reveals and follow-path tracks. `viewer.getObject(id)` → the loaded `THREE.Object3D` (escape hatch: the viewer guarantees the id mapping, not the object's internals), and **`handleMessage()` returns the reply payload** for query messages (`list_objects`/`query_scene`/`get_camera`) via a `_reply()` capture, so no-WS embedders get answers as the resolved value. `viewer.addOverlay(object3D, {id, includeInBounds})` / `removeOverlay(idOrObject)` — embedder-owned scene mounts: excluded from framing/scene bounds unless `includeInBounds: true`, untouched by scene `clear` and the animation system, never disposed by the viewer (re-using an id replaces). `viewer.setStatus(text, state)` (`connected`/`disconnected`/`neutral`) drives the header chip, which under `autoConnect: false` now defaults to a neutral "Local data" instead of "Waiting for Python...".
- **Embedder load-progress API** (issue #163): `viewer.onLoadProgress(cb)` / `viewer.onAssetsLoaded(cb)` / `viewer.getLoadState()` — the public replacement for polling the private `_pendingFetches` counter (which ribweaver's /calib lane did, with a deadline fallback for when the private name changes). All three speak one snapshot, `{loaded, total, pending, assetsComplete}`. Binary payloads are fetched over HTTP **as their messages arrive**, so there is no honest up-front total; the counters describe the current **load batch** instead — a batch opens when `_pendingFetches` goes 0→1 and closes when it returns to 0, `total` is the number of fetches *started* in that batch (a running count of what has been seen, which may grow mid-batch — never a prediction) and `loaded` how many of them finished. The finished batch's counters are retained while idle and reset by the next batch's first fetch, so the last progress event stays valid. `onLoadProgress` fires on every fetch start and every fetch end; **`pending === 0` is the honest "spinner off" signal** (everything the viewer knows about has landed) and does not promise the producer has no more messages coming. `onAssetsLoaded` is the stronger signal — it fires when the batch drains *and* the producer has declared its stream complete via `mark_assets_complete` (Python's `wait_for_assets()` sends it; a no-WS embedder feeds it through `handleMessage()` after its last add), and may fire again if further assets arrive after a completion. It is the browser-side twin of the existing `assets_loaded` WS notification: `_maybeNotifyAssetsLoaded` still gates the *socket send* on an open WS, but the **hooks are ungated**, which is the whole point — a no-WebSocket page driving `handleMessage()` directly was exactly the case the old WS-OPEN early-return locked out. House hook idiom: each `on*` returns an unsubscribe fn. JS-only (no Python/WS surface).
- **Resize coalescing** (issue #128): each real `resize()` is a full GL realloc (renderer framebuffer + EDL render targets), so the container `ResizeObserver` is rAF-coalesced — a burst of resize events (fast splitter/window drag) records only the latest size and applies at most one `resize()` per animation frame (the last recorded size always lands) — and `resize()` itself no-ops when width/height equal the last applied size, which also guards embedders that call `viewer.resize()` directly per mousemove (ribweaver panel/boat). Zero-size (hidden container) rects still early-return without recording a last-applied size, so the first real size always applies.
- **WS-decoupled dispatch**: The control-message switch lives in a public `viewer.handleMessage(data)` method; `connect()`'s `onmessage` only parses the WS frame and delegates to it. This makes no-WebSocket / static-page embedding first-class — construct `new ThreeJSViewer(container, { autoConnect: false })` (already supported) and feed messages straight in (`viewer.handleMessage({ type: 'add_points_binary', id, blob_url, ... })`) with no `websockets` server. Binary payloads still load over HTTP (static files or in-page `Blob` object URLs) exactly as under the socket transport. Query messages that expect a reply (`list_objects`, `query_scene`, `get_camera`) route their response through `_reply(payload)`, which sends over the socket when one is connected and always returns the payload — the query cases return it straight out of `handleMessage()`, so no-WS embedders get the answer as the resolved value (per-invocation, no shared capture state). **Unknown-message hook** (issue #145): `viewer.onUnknownMessage(cb)` — sanctioned extension point for application-defined message types (retires ribweaver /sim's `ws.onmessage` monkey-patch): `handleMessage`'s `default:` branch fires every registered callback with the parsed message, so it covers both the WS transport and direct `handleMessage()` calls; while ≥1 callback is registered the `Unknown message type` console.warn is suppressed (the app has claimed the type), with none it warns as before. Known viewer types never fire it. House hook idiom: each call returns an unsubscribe fn. JS-only (no Python sender).

### Animation Modes
- **Streaming mode**: Real-time updates from Python (`batch_update()`, `set_matrix()`)
- **Looping mode**: Pre-computed frames with interactive playback (`load_animation()`)

### Animation lifecycle
- **`load_animation(anim)`** — first call (no animation loaded yet) starts at t=0; playback begins immediately unless `autoplay=False`. Subsequent calls preserve the current playhead time (clamped to the new duration), play state, and camera-tracking — only the underlying frame data is swapped. Pass `restart=True` to force the first-load behavior (reset to t=0, re-install camera-tracking) on a swap; `autoplay` still governs play/paused on a restart. `autoplay=False` has no effect on a swap without `restart` (prior play state is preserved). Pass `initial_time=<seconds>` or `initial_time="end"` to land the playhead at a chosen time on first load / restart (ignored on a swap) — pairs with `autoplay=False` for "paused at completion". Pass `loop=True|False` to override the animation's baked `loop` flag (omit to use `anim.loop`).
- **`pause_animation()` / `resume_animation()`** — pause/resume at the current playhead. No-op if no animation loaded.
- **`unload_animation(restore_visibility=True)`** — exit animation mode entirely: re-enables `matrixAutoUpdate` on every object (animation pins it off), resets every draw range to 1.0, optionally restores baseline visibility, hides the controls UI. This is **not** a pause. Replaces the older `stop_animation()` / `clear_animation()` (use `restore_visibility=False` for the old `clear_animation` semantic).
- **`set_follow_path(id, times, positions, axes)`** — attach a *follow-path track*: object `id` rides a timed 5-axis path, its pose computed **per render tick from the real path** at the current animation time (binary search on `times`, tip position lerped, tool axis nlerped, minimal rotation of the object's local `+z` onto the axis; the object's own scale is preserved). Use it for a 1:1 tool body: animation frames may sample a long timeline coarsely (e.g. 10 Hz `transforms`), but the tracked object still hits every path point exactly — no keyframe aliasing on a fast toolpath. Payload is binary (`(K,)` non-decreasing **float64** seconds followed by `(K,3)` tip positions + `(K,3)` unit axes packed as float32 `[px,py,pz,ax,ay,az]` rows, K≥2, fetched via the blob sidecar). Times are float64 on purpose: float32's ulp is ~4 ms at t=40,000 s and ~16 ms at 160,000 s, which on hours-long timelines jitters the tool visibly and collapses ms-spaced keys to dt=0 (hold-then-jump stutter); positions/axes stay float32 (mm-scale geometry is fine). The track drives the object whenever an animation is loaded (it reads the animation clock; it composes `obj.matrix` directly with `matrixAutoUpdate` pinned off, overriding any `transforms` channel for that id). Tracks are per-id (a re-send replaces), dropped on `delete`/`clear`, and follow-path objects are the **preferred camera-tracking target**: the `T` track cycle (off → follow → look-at) picks a follow-path id before falling back to transform-channel name hints (`nozzle`/`tip`/`tool`/`effector`).

### Supported Object Types
- **Groups**: `add_group(id, parent=...)` — empty transform nodes for parent-child hierarchies. Children inherit parent transforms. All `add_*` methods accept an optional `parent` parameter. **Deferred re-parenting** (issue #138): a child whose named parent isn't registered yet (parent model load in flight, or out-of-order messages) is added at the scene root so it still renders, with the desired parent recorded (`userData.__pendingParent` + a viewer `_pendingReparent` map); the single registration choke point `_registerObject(id, obj)` (used by every add path) re-parents waiters via plain `parent.add(child)` — NOT `attach`, because the child's transform was authored parent-local at add time, so `add` reproduces the intended pose while `attach` would bake the wrong scene-root world pose — and bumps `_objGeneration`/scene bounds so framing notices the moved subtree. Deleting a waiting child prunes its pending entry (an unrelated later object reusing the id is never mis-parented); deleting/re-adding the would-be parent id keeps waiters (same id = same logical object); scene `clear` drops all pending entries.
- Primitives: box, sphere, cylinder, capsule (with optional roughness/metalness)
- **Shader floor grid** (issue #126): `add_grid(id, cell_size=1.0, extent=100.0, line_width=1.5, color=0x555555, center_color=None, background_color=None, background_opacity=0.0, fade_start=0.5)` — a first-class, anti-aliased, distance-faded grid plane (the ShaderMaterial look from ribweaver's `geometry-loader.js` prototype; distinct from the fixed `show_grid` `THREE.GridHelper` toggle, which stays). One `PlaneGeometry` + `ShaderMaterial` (`buildFloorGridMesh` free function): line distances are measured in screen pixels via `fwidth`, so `line_width` (px) is screen-space stable at any zoom/grazing angle with 1px smoothstep AA; a cell-density attenuation fades lines out where a cell spans under ~4 px (grazing angle / distance) instead of letting the grid collapse into a solid sheet; the two axis lines through the local origin draw in `center_color`; a radial alpha fade from `fade_start`×half-extent to the edge dissolves the finite plane into an "infinite" floor; optional translucent fill between lines via `background_color`/`background_opacity`. The fragment shader ends with the `tonemapping_fragment`/`colorspace_fragment` chunks so it follows the renderer's tone mapping like built-in materials (incl. under the EDL composer). Tracked in `_objects` (id, `delete`, `set_visibility`, transform, `parent`, dropped by `clear` — multiple grids can coexist), but **excluded from framing bounds** (`userData.excludeFromBounds`, honoured in `updateSceneBounds`, so a big floor never inflates double-click/F framing) while the **near/far fit still reaches it** — `updateSceneBounds` keeps a second `_nearFarSphere` = content ∪ bounds-excluded furniture and `updateNearFar` fits against that (identical to `_sceneSphere` with no grid present), otherwise a grid larger than the content hard-clips at the content-fitted far plane; the fog fallback stays on the content sphere (fog is polyline-scoped). **Never raycast** (`mesh.raycast` no-op — `viewer.pick` and gizmo click-select pass through it), and **skipped by the `M`/`N` debug cycles** (`userData.isGrid` guards in `applyWireframe`/`_forEachUserMesh` — a material swap would turn the shader plane into an opaque sheet). Plane lies in local XY (Z-up floor at z=0); position/rotate/parent to place. Depth cues don't apply (fog scope force-disables fog on non-polyline materials; ShaderMaterial ignores it anyway).
- Polylines: gradient-colored with colormaps (viridis, plasma, turbo). `add_polyline(..., fat=False)` renders a native `THREE.Line` (one vertex per point, ~1px, one draw call) instead of the default fat `Line2` — far lighter for million-point toolpaths, but WebGL ignores `line_width`. Per-vertex colors, `set_draw_range`, the `draw_ranges` channel, and `update_polyline_colors` work on both paths. `add_polyline(..., segments=True)` renders disjoint line *segments* instead (`THREE.LineSegments`: consecutive point pairs each draw an independent edge) — many separate episodes in one object/draw call with no false connectors; requires an even point count, implies the native path (`fat` ignored), and is never pickable (an edge soup has no arc length).
- Meshes: pre-built triangle meshes via `add_mesh()` with optional vertex colors and normals
- Beads: toolpath extrusion via `Toolpath` + `add_toolpath()` — convenience wrapper around `add_parametric_tube` with colorize support. Zero-width segments (travel moves) collapse to degenerate points for natural taper transitions. **Travel-move rendering** (issue #88): `add_toolpath(..., travel="line", travel_color=0x666666)` also draws the travel hops themselves — every spine edge not interior to an extrusion run (each hop spans from the last extruded point through the zero-width points to the next extruded point) as **one** `segments=True` native line child (`<id>_travel`, single draw call for any number of disjoint episodes). Wired into the group's draw-range distribution by contract: `register_toolpath_group` carries `travelId` + ascending `travelEndFracs` (global spine fraction of each edge's end point, same `/n_total` convention as `segmentRanges`), and `applyToolpathGroupDrawRange` binary-searches them to reveal whole hop edges in lockstep with the beads — robust where the draw-a-line-under-the-bead occlusion trick broke (`opacity < 1`, LOD thinning). With `travel="line"` even a single-run toolpath with travel gets the group form (the bare-tube fast path has nowhere to hang the mapping); without travel stretches the option is a no-op. **Single-point extrusion runs** (travel in → one deposit → travel out, issue #103) are skipped rather than raising (a tube needs ≥ 2 spine points) — both edges flanking an isolated point are travel edges, so `travel="line"` keeps it covered, and `segmentRanges`/`travelEndFracs`/the bias ramp keep global spine indices so the bookkeeping stays monotonic; a toolpath whose runs are *all* single points degrades to a travel-only group (`travel="line"`) or a clean no-op. See `examples/15_toolpath_interrupted.py`.
- **Parametric tubes**: `add_parametric_tube(id, spine, widths, heights, colors=..., anchor="center")` — variable-cross-section extruded tube built on the client from per-spine-point parameter arrays. Chamfered hexagonal cross-section (45° chamfers, 6 vertices per ring) with constant-up frame derivation (V anchored to global +Z). Corner handling: directional miter — the cross-section stretches by 1/cos(half-turn) along the actual turn direction projected into the section plane (so vertical layer-change elbows stretch along V instead of flaring sideways), bevel past `TUBE_MITER_LIMIT = 2` (turns sharper than 120°; exactly-120° sits on the strict gate boundary and may resolve either way per float rounding); frames freeze across near-vertical tangent runs (|T·up| > 0.99 — interior riser samples copy the nearest out-of-cone neighbor's frame instead of seeding V from the fallback axis); zero-length spine segments (exactly-coincident duplicate vertices, e.g. a sharp width-step twin ring) do **not** snap the frame tangent to +X (issue #117) — the seed scans forward to the first non-degenerate segment and the rolling update carries the previous direction through a degenerate one, so a duplicate at a bend renders as a clean step instead of a fold-fan shard (shared by the main-thread build and the LOD worker via `computeMiterFrames`); and a deposition-order bias scales each ring up by ≤0.1% about its anchored section centre (per-ring anchor offsets `vOffs` are captured from the unbiased heights, so the anchored face separates too) so an exact retrace (A→B→A) nests the later-deposited leg outside the earlier one — the visible surface is deterministically the last bead laid; `add_toolpath` threads one global ramp across travel-split segment tubes via `bias_index_offset`/`bias_index_total`. `anchor="center"` (default) centers the bead on the spine; `anchor="top"` places the spine at the top surface so the bead extends downward (useful when the spine represents a nozzle-tip toolpath). Revolution surface end caps. **Per-draw index cap** (issues #113/#114): a tube whose index buffer exceeds the WebGL per-draw limit (`webgl.max-vert-ids-per-draw`, 30M on Firefox/ANGLE; driver-dependent, not reliably queryable) is silently truncated by the GPU — the tail vanishes with only a console warning. `applyTubeDrawCap` splits any tube over a conservative `MAX_TUBE_INDICES_PER_DRAW = 24_000_000` into `geometry.addGroup` chunks (whole-triangle-aligned, ≤ cap) + a 1-element material array, so three.js issues one `drawElements` per group under the cap; tubes under the cap keep a single material and no groups (byte-identical to before). Groups partition the index buffer positionally and the r183 renderer intersects `geometry.drawRange` with each group, so the single `setDrawRange(0, N)` reveal + endCap relocation span chunks unchanged. Runs on both the non-LOD build and every LOD-worker geometry swap, so an LOD tube that refines past the cap on a close-in zoom is chunked too rather than truncating again (#114 subsumed). Test seam: `window.__tubeDrawCapOverride` lowers the cap for browser tests. **Break mask** (`break_before=`, issue #107): an optional `(N,)` bool/uint8 mask; a non-zero entry at index `i` breaks the ribbon before spine point `i` (the ring pair `(i-1, i)` is not stitched), so a genuine interior discontinuity — a rapid/travel hop between two separate parts, or an end-wipe across empty space — renders as two disconnected strips instead of a stray cone bridging the gap. Each break's two open ends get a **flat fan cap** (dedicated axial-normal rim verts appended after the revolution caps); the cap fans are emitted **inside the broken pair's own fixed 36-index slot**, so `draw_range`/animation pacing and the whole ring-pair→index layout are byte-for-byte identical to the un-broken tube (a `None`/all-zero mask sends no trailing bytes and is byte-identical on the wire — `hasBreakMask` header flags its presence, with a leftover-bytes auto-detect fallback for producers that append the block without the flag). Breaks **survive LOD**: the mask is remapped onto the reduced spine (a reduced pair breaks if any original break falls in its spanned index range), threaded through both the main-thread sync fallback and the worker rebuild. `break_before[0]` has no pair before it and is ignored. Supports `draw_range` with smooth frontier-ring morphing (the next ring's vertices are lerped to the interpolated spine position for pixel-smooth growth), the `draw_ranges` animation channel, and cheap color-mode swaps via `update_parametric_tube_colors(id, colors)`. **LOD**: tubes with ≥25k spine points get automatic distance-weighted RDP simplification — a Web Worker runs chunked RDP (chunk size 5000, epsilon = camera_distance / 2500) and builds the reduced geometry off the main thread. Per-chunk results are cached and reused when the camera distance to the chunk midpoint changes less than 50%. Chunks are sequential spine spans (not spatial), which is required to preserve draw_range ordering and frontier morphing continuity. LOD updates are throttled to 2 Hz. The per-frame LOD-dispatch skip gate uses the camera's **actual distance to the tube's bounding-sphere surface** (world-transformed, floored at 1% of the bounding radius, capped by the old 2×radius model-size proxy), not an absolute model-sized threshold (issue #118): close-in zooming moves the camera a few cm while the LOD epsilon (∝ camera distance) shrinks an order of magnitude, so the old model-size gate never re-fired and a stale coarse tube rendered up close; the surface-distance gate re-triggers the worker on small close-in moves while behaving as before far away. Per-tube LOD overrides via the optional `lod=` kwarg on `add_parametric_tube` (also passes through `add_toolpath(**kwargs)`): pass `lod=False` to disable entirely, or `lod={"epsilon_divisor": N, "threshold": M}` to tune detail retention and the spine-length gate (use `threshold=0` to force LOD on below 25k).
- **Tube strand-collapse** (`add_parametric_tube(..., strand_collapse=...)`): opt-in fold-collapse pass (`collapseTubeStrandFolds`) for tight inside corners / wipe loops where the bead is wider than the local turn radius so a centre-line-swept tube self-intersects — it detects fold targets on each cross-section-vertex strand polyline (seg-seg distance-grid local minima) and snaps the inside-bend rings across the fold range to the closest-pair apex, turning self-intersecting fans into clean creases (top-view footprint preserved). `strand_collapse=True` for defaults, or a dict: `max_snap_factor` (default 0.5) caps per-ring displacement in bead-widths — the full-bead reach (1.0) over-snaps *tight* folds into a spiky-cusp + z-fighting-seam artefact, while dropping too far (0.25) under-shoots real wide-bead corners (strands stop short of the apex → protruding wedge); 0.5 reaches the apex on real corners identically to 1.0 (0.00% pixel diff vs the #50 tuned bulb baseline) while staying gentle enough to avoid the tight-fold fin; `large_seg_factor` (default 1.0, issue #119) **exempts rings on open straights** — a ring whose shorter adjacent spine segment is ≥ this many bead-widths is treated as outside any wipe-loop fold and never moved, no matter what the detector claims, confining collapse to genuinely dense regions and removing false snaps from degenerate tangents at nearby micro-segments/breaks (`0` = exemption off). The pass runs on the LOD worker (`collapseOnly` message for non-LOD tubes, or the reduced-spine rebuild for LOD tubes) so the main thread never blocks; both buffers are retained so the current bead can be toggled live with the `S` key or `set_strand_collapse_enabled(id, bool)`. Runs are deterministic; the exemption is inert on genuine dense folds (all-short-segment wipe loops) and only ever *skips* a snap, never adds one.
- **Swept tool body (5-axis)**: `add_swept_tool(id, positions, axes, profile, colors=..., sections=16, color=..., opacity=1.0, metalness=.., roughness=..)` — swept *oriented* tool-body tube for 5-axis toolpaths. The crux vs `add_parametric_tube`: it **decouples the extrusion axis from the path tangent**. At each station `k` the `(height_along_axis, radius)` `profile` (M×2, revolved into rings of `sections` verts) is lofted about the **tool axis** `axes[k]` (unit, tip→holder — generally *not* the path tangent), centred at `positions[k]`, and consecutive stations are connected into a swept surface (the swept shank/holder of a tilting tool — reveals reorientation-rate "wrist speed" and tool-body collisions the cutting-tip envelope can't). Geometry built client-side by the in-file free function `buildSweptToolGeometry`: per densified profile level a ring is lofted along the path (per-level swept tube), straight profile runs are **densified in height** so a sparse profile still sweeps a continuous wall, with revolution end caps at the first/last station; a per-station constant-up frame (V anchored to +Z, +X fallback near-vertical) keeps rings from twisting. Per-station `colors` are packed `uint32 0x00RRGGBB` (like the tube), linearly interpolated along the path; `MeshStandardMaterial` (DoubleSide, `opacity<1` → translucent so the part shows through for collision reads). Index order is station-major so `set_draw_range`/`draw_ranges` reveals the body along the path (`userData.isSweptTool` + `totalIndexCount`). The linear loft can pinch/self-intersect on the inside of a sharp axis swing — accepted (faithful surface, not a boolean solid). Tool-body picking and LOD are not wired for this primitive.
- **Point clouds**: `add_points(id, positions, colors=..., colormap=..., color=0xFFFFFF, size=2.0, size_attenuation=True)` — GPU point cloud rendered as a single `THREE.Points` draw call (native `THREE.PointsMaterial`), for massive unconnected clouds (voxel fields, metrology/deviation clouds, LiDAR scans) where `add_polyline` would wrongly connect points and one primitive per point is too heavy. Binary transfer of `positions (+ colors)` like `add_polyline`; per-point colours via the same `_apply_colormap` path (scalar→colormap, or `(N,3)` RGB, or a flat `color` fallback when `colors=None`). `size` is the base point size in px; `size_attenuation=True` (default) shrinks points with distance (perspective, viewport-aware), `False` draws a constant pixel size. Supports `set_draw_range`/`draw_ranges` (reveals the leading `frac*N` points of the buffer — order points along a toolpath for a cheap material-removal animation). Flat `THREE.Points` covers ≤~10M points comfortably; larger clouds use the octree LOD tier below. Picking is not wired for points (the arc-length `PolylinePickController` is spine-based). **Incremental append**: `append_points(id, positions, colors=None)` grows a flat cloud created by `add_points` **in place** — only the new points cross the wire (`append_points_binary` header + blob) and the viewer writes them into spare capacity at the tail of the existing buffers (`addUpdateRange` → a `bufferSubData` of the new points alone), so a live producer (a laser tracker at 1 kHz flushed a few times a second for hours, growing toward ~10M points) costs O(new) per update where re-sending the whole cloud via `add_points` is O(total) and dies around 1e5 points at ~4 updates/s. Capacity doubles when it runs out (floor `POINTS_APPEND_MIN_CAPACITY = 1024`): `ensurePointsCapacity` moves the data into a **fresh** `BufferGeometry` and `dispose()`s the old one, because a replaced-but-not-disposed attribute leaks its GL buffer; it also **carries the bounding box/sphere across** to the new geometry, since `expandPointsBounds` re-seeds its box with an O(count) scan whenever `boundingBox` is missing — dropping them would make the one append that happens to trigger a doubling re-scan the whole cloud (amortised still linear, but a visible latency spike on a multi-million-point stream). Appends are **serialized per id** (`_pointsAppendChain` in `handleMessage`) — the blob fetches complete out of order otherwise, and buffer order is the `draw_range` prefix contract. Bounds are expanded from the new points only (`expandPointsBounds`: box exact, sphere = the box's circumsphere, a safe over-estimate — `computeBoundingSphere` would be O(total) per append); the draw range follows the growth only when the cloud was fully revealed, so a partial `set_draw_range` reveal is left where it is. **The colormap range is frozen at `add_points` time** (`cmin`/`cmax` stored per id): a later chunk clamps at the ramp ends rather than rescaling, since rescaling means re-colouring — and re-uploading — every point already there; pass explicit `cmin`/`cmax` when the range is known up front. Python tracks flat clouds per id (`_points_flat`, dropped on `delete`/`clear`/replace-by-LOD), so an append to an id it never created **raises `ValueError`** rather than vanishing; the viewer additionally warns per append for a cloud it does not have — which is exactly the **browser-reload-mid-stream** case: nothing replays a point cloud on reconnect, so re-seed with `add_points`. Not supported on octree-LOD clouds or on clouds with `birth_times`/`removal_times` (both raise). Append blobs are evicted past `_APPEND_BLOB_HISTORY = 256` chunks — one blob per update forever would otherwise retain every point an hours-long stream ever sent — and a cloud's remaining chunks are dropped by `delete`/`clear` (`_drop_append_blobs`, blob keys tracked id-tagged): the cap bounds a *running* stream, but a deleted cloud is never appended to again under that id, so a stream that stopped under the cap would leave its chunks in `_blob_store` for the life of the process. **Per-point time window**: `add_points(..., birth_times=..., removal_times=...)` attaches optional (N,) per-point lifetimes — the vertex shader shows a point only while `birth_time <= t < removal_time` against a per-cloud scrub-time uniform (culled points get `gl_Position` shoved outside the clip volume: clipped pre-raster, zero fragment cost — Potree's GPS-time-filter trick, patched into the stock `PointsMaterial` via `onBeforeCompile` + a `customProgramCacheKey` per attribute combination). This expresses **out-of-order** appearance/removal that `draw_range`'s buffer-prefix reveal cannot (issue #79: material removal isn't a prefix). NaN/±inf ends mean unbounded (NaN birth = always existed, NaN removal = never removed; Python maps them to ±FLT_MAX because GLSL NaN compares are undefined). The scrub time starts at 0 and is driven by `set_points_time(id, t)` (streaming; validates finite, no-ops on objects without a window) or the `point_times` animation channel (`Animation.set_point_time_data` / `Frame(point_times={...})`) so the animation slider scrubs points in/out; the uniform object is shared by reference into every program compiled from the material (incl. the EDL depth pre-pass), so scrubbing touches no material state. `unload_animation` leaves the scrub time untouched (there is no universal "all visible" time once birth and removal both exist). **Octree LOD** (`add_points(..., lod=True)` or a dict of `node_capacity`/`point_budget`/`refine_pixels`/`max_depth`/`seed`; design + prior-art rationale in `plans/points-octree-lod.md`): for clouds beyond the flat tier, Python builds a Potree-style **additive sampled octree** (`points_lod.py` — every node owns a seeded pseudo-random sample of its cube, **time-stratified** over birth/removal times so the time filter thins every LOD level uniformly; children add detail, no point stored twice; per-node sample vertex order is Morton-sorted then shuffled in 128-point batches for raster throughput). The cloud is reordered so each node is a contiguous slice; the browser gets one `add_points_lod` WS message + a 40 B/node binary hierarchy blob (bounds, count, `[min birth, max removal)` time bounds, BFS `first_child`/`child_mask` topology), and **node payloads stream on demand**: per-frame priority traversal (`_updatePointsLOD`, max-heap on projected node size) refines while a node projects ≥ `refine_pixels` and stops adding at `point_budget` (default 1.5M); missing wanted nodes are fetched (≤6 concurrent) from lazy **callable blob-store providers** that quantize + pack a numpy slice per request (`GET <sidecar>/points_lod_<uuid>/<i>`), and loaded-but-unwanted nodes LRU-evict past ~3× budget. Node payload: **normalized int16 xyz** over the node cube (dequantized free via normalized attributes + the node `Points`' center/scale transform — ints stay GPU-resident, unlike Potree's CPU float decode) + u8 rgb + f32 birth/removal (u16 time quantization deferred: needs an immortal-flag sentinel). **Grid fast-path**: for lattice-aligned clouds (voxel centres) pass `lod={"grid": {"spacing": pitch}}` — `build_points_octree_grid` builds the same octree via one global uint64 Morton code + one sort (every octree cell at every level is then a contiguous range; octants split by `searchsorted`, no per-node re-partition), ~4× faster than the float builder and flat in N (8M ≈ 1.1s vs 4.4s). Result is structurally identical; sampling is a plain strided (spatial) subsample — `strat_times` accepted but ignored, because carve removal times are spatially correlated so a spatial sample stays honest under the scrub, and skipping the time sort keeps the build reproducible for external producers. An external producer (mill-sim's Rust kernel) can pre-supply `"codes"`/`"order"`/`"n_bits"` (global Morton codes + their sort permutation) and the builder skips its two super-linear stages; the bit-exact contract lives in `docs/points-lod-grid-api.md` with `grid_morton_codes()` as the Python reference. Only declare `grid` for genuinely lattice-aligned clouds — the bit-slice octant test matches the float `pos > centre` test exactly only for cell-centred points. `lod={"size_boost_max": k}` (default 2.0, `>= 1.0`, 1.0 = off) caps the coarse-node point-size fattening per cloud; the header field is `sizeBoostMax`. **Runtime tuning**: `set_points_lod_options(id, point_budget=, refine_pixels=, size_boost_max=)` re-tunes a streamed cloud live with no re-upload or octree rebuild (issue #87 — the traversal reads these fresh every frame; a `size_boost_max` change also re-derives the point size on already-streamed node materials via the shared `lodNodeSize(lod, i)` free function). Fields left `None` are unchanged; values are transient viewer state like `set_camera` (a browser refresh reverts to the add-time `lod=` options). Per-node explicit bounding sphere/box (frustum culling per node); nodes whose time bounds miss the scrub time are skipped for draw *and* fetch (scrubbing to a dead region costs nothing) but still descended. Coarse nodes draw slightly fatter points (√2/level, capped 2× — aggressive boosts turn coarse ancestors into giant occluding sprites near the camera). The group carries the shared `userData.timeUniform`, so `set_points_time`/`point_times` address a LOD cloud identically to a flat one. Caveats: **the Python process must stay alive to serve refinement** (loaded nodes survive, deeper zoom won't sharpen without the server); `set_draw_range`/`draw_ranges` are no-ops on LOD clouds (buffer order is per-node Morton — use the time window); picking not wired; client-side state is released on `delete`/`clear`/re-add (`_release_points_lod`).
- 3D models: GLTF/GLB, STL, OBJ, FBX, DAE, PLY, 3DS
- **Draco-compressed glTF/GLB** (issue #167): `KHR_draco_mesh_compression` assets load through the normal `add_model`/`add_model_binary` path — both `GLTFLoader`s get one shared `DRACOLoader` (`viewer._dracoLoader`, one worker pool) via `setDRACOLoader`. The extension is per-primitive and GLTFLoader falls back on its own, so **uncompressed assets are byte-identical to before** and the decoder stays cold: `DRACOLoader` only inflates the wasm and spins a worker on the first compressed primitive, so an all-uncompressed scene never pays for it. **The decoder ships inside the bundle — there is no CDN fallback at any level** (prod runs offline behind a firewall). `build.py` gzips `static/draco/draco_decoder.wasm` + `draco_wasm_wrapper.js` (deterministically, `mtime=0`) and base64s them into the `DRACO_DECODER_DATA` constructor option; gzip+base64 costs **~101 KB** in `viewer.html` (686 KB → 790 KB, +15%) where raw base64 of the same files would be ~334 KB (+49%) — the wasm is highly compressible and `DecompressionStream('gzip')` inflates it natively. The free function `createDracoLoader(options)` resolves the decoder in precedence order: (1) `options.dracoDecoder` = `{wasmGzB64, wrapperGzB64}` (the `viewer.html` path — works under `file://`, which is what the browser test exercises); (2) `options.dracoDecoderPath` = a URL prefix an embedder serves the two files from (three's `setDecoderPath` contract, trailing slash); (3) `static/draco/` resolved against `import.meta.url`, for an embedder serving the `viewer/` source directory as static files. The inline path works by overriding **`DRACOLoader._loadLibrary(url, responseType)`** — the single private seam where the class turns a decoder filename into bytes (normally a `FileLoader` GET under `decoderPath`) — so the worker pool, decoder config, and `dispose` are all untouched, and `decoderPath` stays `''` (no URL is ever constructed). Being a private method it is pinned to the vendored decoder pair and to `build.py`'s `THREE_VERSION`; a three upgrade that renames it fails loudly on the first Draco asset and in the browser test. A WebAssembly-less browser (which could not run the viewer anyway) gets a clear rejection rather than a silent pure-JS-decoder fetch. Re-encoding an existing corpus (`gltf-transform draco` / `gltfpack`) is a producer-side change, not a viewer one; `EXT_meshopt_compression` is **not** wired.
- **Embedded clip animation (GLTF/GLB)**: models with baked animation clips get a `THREE.AnimationMixer` (in `_mixers`) whose actions are **created but not played on load** (issue #135) — the authored bind pose holds until the first clip-drive message, instead of the old eager `play()`+`setTime(0)` statically pinning every node to its t=0 keyframe (a bellows clip's t=0 is maximally compressed, so undriven models looked "scaled"). The drive paths all funnel through the free functions `driveMixerTime`/`driveMixerProgress` (which activate the deferred actions on first use, identical behavior to before thereafter): `set_clip_time(id, seconds)` (absolute seek), the binary `clip_times` animation channel / `Frame(clip_times={...})`, and **`set_clip_progress(id, t)`** — normalized `t` clamped to [0,1] on the viewer side and mapped to `t * duration` **per clip** (each clip uses its own duration), so a caller can drive a baked 0..1 clip straight from an axis fraction without knowing seconds (Python validates `t` finite; one-time console warn on objects without clips). **All clip seeks clamp at the clip end** (issue #143): actions loop (`LoopRepeat`), where a seek to exactly `duration` wraps modulo the clip back to the t=0 pose — a 0..1 drag-chain clip driven by normalized rail position looked right at 99.98% travel and snapped to fully-compressed at 100%. Both drive functions now route through `seekMixerActionsClamped`, which sets `action.time` **per action** clamped to `[0, duration·(1−1e-6)]` (per action because one model's clips may have different durations — a single `mixer.setTime` would wrap each independently), then `mixer.update(0)`. So `set_clip_time(D)` / a `clip_times` channel value ≥ D holds the end pose, a negative time holds the start pose, and `driveMixerProgress`'s existing progress-1.0 back-off is the same clamp. Deliberate trade-off: a `clip_times` channel can no longer sweep past D to loop a clip (it saturates) — a producer wanting looped playback emits modulo-D times itself; nothing in the repo relied on wrap, and ribweaver's interim `min(t01, 1−1e-4)` workaround becomes unnecessary. Discovery: `query_scene` entries additively carry `clipDurations` (array of seconds) for objects with a mixer.
- **draw_range**: polylines, meshes, parametric tubes, *flat* point clouds, swept tool bodies, and **loaded models** support `set_draw_range(id, 0.0-1.0)` to control visible fraction, and `draw_ranges` channel in animation frames. **Loaded models** (issue #104): after any model load (`add_model`/`add_model_binary`, all formats), `stampModelDrawRangeMeshes` stamps every descendant mesh with `userData.isMesh`/`totalIndexCount` (mirroring `add_mesh_binary`); a non-mesh root (GLTF/GLB group wrapper etc.) is marked `userData.isModelGroup` with the stamped-mesh list retained, and both draw-range dispatchers (`_setDrawRange` + the binary `draw_ranges` channel applier) apply the fraction **per child mesh** via `applyModelGroupDrawRange` — intended for assets authored with primitives ordered along the reveal axis (e.g. rail bellows GLBs). An STL/PLY root *is* a mesh, so the stamp alone routes it through the existing `isMesh` branch. `query_scene` reports a model group's `drawRange` from its first stamped child (the group has no geometry); `unload_animation`'s reset-to-1.0 restores all children. The absolute start/count window form from the issue is deferred. Two LOD systems differ here on purpose: **tube LOD keeps draw_range** (the viewer remaps the fraction onto the reduced geometry by arc length, `remapDrawRangeToReducedPairs`), while **octree-LOD point clouds (`add_points(lod=...)`) do not** — their buffer is per-node Morton order, so a leading-fraction prefix is spatially meaningless; drive per-point visibility with the birth/removal **time window** instead (which is also the only mechanism that can express out-of-order removal). The viewer warns once per LOD cloud if a draw_range is sent at it. One `draw_ranges` channel can drive **multiple objects of different types in lockstep** — `set_draw_range_data([tube_id, line_id, cloud_id], data)` dispatches per `userData` type per object, so heterogeneous reveals (bead + travel line + point cloud) stay on one clock.
- **Polyline / tube picking**: opt-in interactive picking of a point *along* any polyline **or parametric tube** (the "bead"), owned by the in-file `PolylinePickController`. Enable from Python with `enable_polyline_picking(marker_color=..., threshold_px=..., max_pick_points=...)` or `on_polyline_pick(callback)` (the latter also enables it). When on, hovering near a pickable object glides a screen-constant marker to the closest point on its spine and shows a cursor readout of the arc-length fraction; a click (not a drag) sends `{id, kind, fraction, point, local_point, segment, t}` back over the WebSocket, where it is dispatched to registered callbacks. `kind` is `"line"` or `"tube"`; `fraction` is the headline value (position in `[0,1]` along total arc length). **Movement is continuous — the marker never snaps to vertices.** Picking is a two-stage hit test (fat `Line2`, native `THREE.Line`, and tubes treated identically): (1) **select** the nearest spine segment by 2D screen distance (nodes projected to pixels) — choosing in 2D means segment *i* ends where *i+1* begins at a shared node, so the hand-off is seamless; (2) **place** the point on that segment via the 3D ray↔segment closest-point (`Ray.distanceSqToSegment`), because a screen-space parameter foreshortens under perspective and would quantize the marker toward the nearer endpoint. The per-object gate is `threshold_px + halfLineWidth` for a line, or `threshold_px + beadHalfExtentPx` for a tube (the bead's half cross-section, projected to pixels per node via the node's view-space depth, so a click anywhere on the bead body — not just its centre-line — registers; the resolved point still sits on the spine). The fraction is read off a retained CPU copy of the local spine points (`userData.pickPoints`) + a lazily-built cumulative arc-length table, so it's exact regardless of the raycaster's reported hit. **For a tube, `pickPoints` is the full-resolution spine (1:1 with the per-spine-point arrays passed to `add_parametric_tube`, independent of LOD), so `segment` is a direct index into the caller's per-point data dimensions** — the basis for looking up other dimensions at the picked point. The trade-off of screen-space selection is no depth ordering between overlapping objects (screen-nearest wins; picking already ignored mesh occlusion). Picking is **opt-out per object**: `add_polyline`/`add_parametric_tube` default `pickable=True`; `pickable=False` drops that object from the pick loop (still rendered, never a target). Picking is inert (zero per-hover raycast cost) until enabled, and **costs nothing at object-add time when never used** — the loaders only stash references to arrays already held (`pickPoints` = the line's point buffer or the tube's full-res spine; plus the tube width/height arrays), and a tube's per-node bead half-extents are built lazily on the *first* pick (`_ensureTubeHalfExtents`), not at load. **Hover cost / huge toolpaths** (issue #111): the per-move scan is O(N) over the spine (project every node to pixels), which on a multi-million-point line dominates the frame budget even though the render is one cheap draw call. Two mitigations: (1) hover picks are **coalesced to one scan per animation frame** — `_onMove` only stashes the latest cursor position and defers the scan to a `requestAnimationFrame` (`_onMoveRaf` → `_doHover`), so a fast mouse move that fires many `pointermove` events runs at most one full scan per frame; always on. (2) `enable_polyline_picking(max_pick_points=N)` (JS: `enablePolylinePicking({maxPickPoints})`) **decimates the coarse scan**: when a spine has more than `N` nodes it's visited with a stride so ~`N` chord-segments are tested (`_scanObjectSegments(..., step=stride)`), the winning object's coarse hit is then **refined at full resolution** in a local index window (`step=1` over `[seg-stride, seg+2·stride]`), so a hover is O(N_pick) not O(N_spine). The resolved `segment`/`fraction`/`point` stay exact (refine runs on the true spine); only nearest-*segment selection* is approximate on sub-stride wiggles. `0` (default) / `<2` = off (exact full scan). Ribweaver's `/sim` gates picking off above 750k points as a workaround; `max_pick_points` is the accelerated path that lifts that gate. Picking state is re-sent on browser reconnect. The marker lives in the scene like the pivot marker (not in `_objects`) so it can't be picked and survives `clear`. `disable_polyline_picking()` turns it off. **Client-side hooks**: a browser embedder can drive picking without a Python round-trip via `viewer.enablePolylinePicking(opts)` / `viewer.onPolylinePick(cb)` (click) / `viewer.onPolylineHover(cb)` (every hover move, payload or `null` on leave) / `viewer.disablePolylinePicking()`. The hook payload is a plain `{id, kind, fraction, segment, t, point:{x,y,z}, localPoint:{x,y,z}}`; registering a hook auto-enables picking, and each `on*` call returns an unsubscribe function. Picks fire both the JS hooks and the WebSocket send when connected.
- **Selection highlight** (issues #147/#158/#165): `set_highlight(id, enabled=True, color=None, style=None, width_px=None, threshold_deg=None)` → `{type:'set_highlight', id, enabled, color?, style?, width_px?, threshold_deg?}` — toggle a persistent selection outline on an object, the missing "this one is selected" primitive for embedders (ribweaver's unified selection). Routed through `_withObject` (unknown-id-tolerant, queues onto an in-flight binary load) to the free function `applyHighlight(obj, enabled, opts)`, which traverses every descendant mesh (so a GLB model group outlines each sub-mesh, like `set_color`) and parents one outline child to the mesh itself — so it follows FK re-posing / animation transforms for free. Two styles:
  - **`"silhouette"` (default, issue #165)** — a true contour: `buildHighlightSilhouette` draws the **same geometry** again with `side: BackSide`, `depthWrite:false`, `toneMapped:false`, and an `onBeforeCompile` patch that pushes each vertex outward along its projected normal by `width_px` (default `HIGHLIGHT_DEFAULT_WIDTH_PX = 3`) **screen pixels** — the offset is applied in clip space and scaled by `gl_Position.w`, so the rim is a constant pixel width at any zoom and under both cameras. Backfaces sit behind the object's own front faces, so the depth test discards them wherever the object covers and only the pushed-out rim survives. The viewport uniform is `viewer._highlightResolution`, shared **by reference** into every silhouette program and updated in `resize()`; `width_px` changes are a uniform write, not a recompile (`material.userData.__highlightWidth`), and the hull **shares the mesh's geometry** (no duplicate buffers — hence `disposeHighlightOutline` disposes only its material). Deliberately depth-tested: a `depthTest:false` hull would paint its backfaces over the object body, so a silhouette highlight is hidden by objects in front of it.
  - **`"edges"`** — the original feature-edge outline (`EdgesGeometry` + `LineSegments`, `depthTest/depthWrite:false`, `renderOrder = 1000`), still **always on top** (shows through occluders) for when the interior structure of the selection matters. `threshold_deg` (default `HIGHLIGHT_DEFAULT_THRESHOLD_DEG = 30`, issue #158) is the edge-detection angle: an edge draws only where its two adjacent faces differ by more than it. THREE's own default is 1°, which on a dense CAD mesh (ribweaver's robot links) or any curved analytic surface keeps nearly every interior edge and reads as an X-ray wireframe — the defect that motivated both the raised default and the silhouette style. Note the flip side: a smooth sphere has *no* crease above 30° at all, so `edges` on a smooth body draws nothing, which is exactly why the hull is the default.

  A **skinned mesh**, one whose geometry has no `normal` attribute, or one that cannot **prime the depth buffer** silently falls back to `edges` (`resolveHighlightStyle`): the hull's basic material is un-skinned and extrudes along the normal, so it would respectively lag the skeleton or collapse onto the mesh — and the hull is culled by the object's own depth, so a mesh that never lands in the depth buffer before it lets the whole hull draw as a **solid shell of the selection colour**. `meshPrimesDepth` requires every material to be both `depthWrite !== false` **and** `!transparent`: `applyOpacity` clears `depthWrite` below opacity 1, but the transparent flag is the subtler half — three.js renders the opaque pass in full before the transparent pass and `renderOrder` only sorts *within* a pass, so the opaque hull always draws before a transparent mesh no matter how high its renderOrder, and a primitive added with `opacity < 1` (where `_createMaterial` sets `transparent` but leaves `depthWrite` true) would otherwise slip through. The style is also **re-resolved when `set_opacity` flips those flags under an already-highlighted mesh** (the resolved opts are retained on `userData.__highlightOpts`, and `applyOpacity` re-applies after its walk rather than mutating the tree mid-traverse), so `set_highlight` → `set_opacity` and the reverse order land identically. **Known wart** (accepted, documented in `set_highlight`'s docstring): a *smooth* translucent body (a sphere, a fillet) falls back to `edges`, which has no crease above `threshold_deg` to draw — so it highlights as **nothing at all** rather than as a shell. Nothing is more honest than a shell that hides the object, and prismatic translucent parts are unaffected, so this is left as-is; the workaround is a lower `threshold_deg` or an opaque-while-selected object. A real fix needs a depth-prime pass (the mesh's geometry drawn `colorWrite:false, depthWrite:true` before the hull), whose own trap is that priming at the object's own surface then makes the object's fragments fail a LESS depth test unless offset. `color` is a hex int or CSS colour string (`THREE.Color` accepts both); default `HIGHLIGHT_DEFAULT_COLOR = 0xffaa00`. Python validates `style` against `_ALLOWED_HIGHLIGHT_STYLES`, `width_px > 0`, `threshold_deg` in `[0, 180]`. **Idempotent**: re-enabling re-tints the existing outline in place and rebuilds only what changed (a new `threshold_deg` swaps the EdgesGeometry, a new `width_px` writes the uniform, a new `style` disposes and rebuilds) — never a second outline (`userData.__highlightEdge` back-reference on the mesh). **Fully reversible**: off removes the child, disposes its material (and its EdgesGeometry, when it owns one) and clears the guard flags — the mesh's own materials are never touched, so the original appearance survives any number of on/off cycles. The outline never intercepts picking: no-op `raycast` like the floor grid. Skipped by the `M`/`N` debug cycles and by `set_color`/`applyOpacity` — all four traversals gate on `userData.__highlightOutline`, which the silhouette hull needs as much as the edge outline does since the hull *is* a Mesh (a wireframe or debug-material swap would turn the contour into a solid shell). Grid meshes and combined-mode wireframe overlays are never outlined. `delete`/`clear` dispose the outline with every other child, and a re-added id starts unhighlighted. Transient viewer state like `set_color`/`set_opacity` — not replayed on reconnect.

- **Line depth cues**: depth-perception aids for flat line drawings (the `add_polyline` fallback for toolpaths too complex to extrude as shaded beads). Two composable cues, owned by the in-file `DepthCueController`. Press `D` to toggle **distance fog** (CAD depth cueing, far lines dim toward near-black via `THREE.Fog` whose near/far are fitted each frame to the closest→furthest view-space depth of the visible lines — `_updateFogRange()` aggregates the per-polyline bounding-box corners in view-Z and anchors `near` to the closest line, but pushes `far` past the furthest so the content spans only `FOG_DEPTH_COVERAGE` (≈0.4) of the white→fog ramp — mapping it into the smoothstep toe so the bulk of the lines stay near the light end (~70% under 0.2 fog) and darkening concentrates on the farthest stretch (furthest ≈0.35). Far lines stay partially lit instead of crushing to fog colour, and the cue tracks the actual content rather than the looser whole-scene sphere. Falls back to the scene-sphere proxy when no line geometry is visible). Press `Shift+D` to toggle **eye-dome lighting** — a screen-space EDL post-process that darkens fragments sitting behind their screen-space neighbours, sculpting line bundles into legible 3D. The two compose (fog dims globally, EDL adds local crossing contrast); a bottom-centre toast names the active state. Also drivable from Python via `set_depth_cue(fog=None, edl=None, edl_strength=None, edl_radius=None)` (each bool toggles its cue; `None` leaves it unchanged; strength/radius re-tune the EDL shader live — stored on the controller so they survive composer rebuilds and can be set before the composer exists) so a script can open straight into fog + EDL, plus a focused `set_edl(enabled=True, strength=None, radius=None)` (new `set_edl` message). **EDL auto-enables the first time a point cloud is added** (flat/LOD both — unlit point quads read as a washed-out sheet without a depth cue); the auto-enable is suppressed once the user *pins* the EDL state (`Shift+D`, `set_depth_cue(edl=...)`, or `set_edl(...)` — `_edlUserSet`), including an explicit OFF, so `set_edl(False)` sticks even for point clouds. EDL lazily builds an `EffectComposer` (`RenderPass` → EDL `ShaderPass` → `OutputPass`) with a shared `DepthTexture` on `renderTarget2` only (attaching it to `renderTarget1` too forms a GL feedback loop). `OutputPass` re-applies tone mapping/sRGB since the scene renders linear into the float target. **`OutputPass` would also tone-map the solid background** (crushing `#222222`→`#101010` under ACES, so EDL-on visibly darkened the viewport vs the direct render), so `renderComposer()` renders the background transparent (`scene.background = null` around the whole composer pass, pre-pass included — a `Color` background's `setClear(color, 1)` GL state persists and would leak an opaque clear into `RenderPass`); the renderer is created with `alpha: true`, the canvas CSS `background-color` is set to the same `#222222` to show through, and the final `OutputPass` is set to `NoBlending` so it *replaces* every canvas pixel (transparent for background, no trails). **Fog does not survive the composer's `RenderPass`**, so the EDL shader re-applies linear fog from depth (`fogMode`/`fogColor`/`fogNear`/`fogFar` uniforms driven from `scene.fog`) — otherwise fog washes out entirely under the EDL overlay. **Both cues are scoped to polyline geometry only** — meshes (cell/fixtures/shaded beads/models) render exactly as with the cues off, so they stay a clean spatial reference. Fog: `scene.fog` is global and every material defaults to `fog:true`, so `_applyFogScope()` force-disables fog on non-polyline materials (saving the prior value on `material.userData._fogScopeSaved` to restore on toggle-off) and enables it only on polylines; it re-runs from `update()` whenever `_objGeneration` changes so objects added while fog is active (incl. async model loads) are scoped too, and also when the `M`/`N` shading-debug toggles change mode (those swap in a debug material or add a wireframe-overlay child without bumping `_objGeneration`, and would otherwise dim under fog). EDL: polylines are placed on a dedicated camera layer (`EDL_LINE_LAYER = 1`, in addition to layer 0) and `renderComposer()` runs a **line-only depth pre-pass** (`camera.layers.set(EDL_LINE_LAYER)` → render into `_lineDepthTarget`) that feeds the EDL pass's `tDepth`; the shader early-outs where line-only depth is far (every non-line pixel), and an occlusion guard against full-scene depth (`tSceneDepth`, the composer's `renderTarget2.depthTexture`) leaves a mesh that sits in front of a line untouched.

- **Camera FOV**: the perspective camera's vertical field-of-view (degrees) defaults to **40°** (a flat, CAD-ish look — was 75°) and is configurable via the `fov` `ThreeJSViewer` option, the `fov` URL query param (wins over the option), or the `ViewerClient(fov=...)` Python kwarg (forwarded as that query param). - **Pre-defined views (view gimbal)** (issues #116/#102; ortho-snap + flip: ribweaver#514): the corner gimbal's six axis bubbles snap to **orthographic** views straight down that axis CAD-viewcube style — `_gizmoAxisClick` → `_snapOrthoAxisView`: switch persp→ortho if needed (`CameraController.switch`), reorient via the `setView` tween — **orbit target, distance, and zoom all kept** (a bubble click must not reset the viewing distance; the persp→ortho switch already matches scale, and there is deliberately no frustum re-fit). **Re-clicking the same axis bubble flips to the opposite side** (`OPPOSITE_VIEW`); the snap state (`_gizmoAxisView`) clears on an orbit/pan drag (gated on `isDragging()` so a plain click-to-pivot keeps the snap) or on leaving ortho, so a later click starts fresh. **Auto-projection** (Blender-style "auto perspective"): view *direction* is the user-facing control and projection follows — a snap that entered ortho marks `_orthoAutoEntered`, and orbiting/panning away from the snapped view (the `isDragging()`-gated snap clear) automatically returns to perspective; a **manual ortho (P/O button or `O` key) is never auto-exited**. The **ISO corner button is a true isometric** — orthographic by definition — implemented as a seventh snap through the same `_snapOrthoAxisView('iso')` path (no flip: `OPPOSITE_VIEW` has no iso entry), so ISO auto-enters ortho and orbiting away returns to perspective exactly like the bubbles. The `⬚ O` toolbar toggle is **removed**; instead a **P/O indicator-toggle button** sits with ISO in a vertical stack just *left* of the gimbal's 128 px square (outside the bubbles' orbit): it always shows the current projection (label `P`/`O` + an `.ortho` accent, synced by `_updateProjButton()` from every persp↔ortho switch, auto or manual) and a click is a manual projection choice (the `O` keyboard shortcut remains too). Any direct `setView` clears the axis snap so a later bubble re-click snaps fresh instead of flipping. **Hover help**: hovering a bubble sets a native tooltip on the canvas (`_gizmoSpriteTitle`) saying what a click does right now (snap to the ortho plan view, or flip when already snapped). Clicking a bubble no longer routes through the stock `ViewHelper.handleClick` — its tween targets hardcoded **Y-up** quaternions (the scene is Z-up, so top/bottom landed with an unpredictable roll) and re-frames around `ViewHelper.center`; instead the click maps the hit sprite via `GIZMO_SPRITE_VIEWS`. `viewer.setView(name)` remains the programmatic surface (`top`/`bottom`/`front`/`back`/`left`/`right`/`iso`, or `home` = `resetView()`). `setView` **keeps the current orbit target and distance** (reorient only, no framing): it slerps the target→camera direction (identity→`setFromUnitVectors` quaternion, smoothstep-eased, `VIEW_TWEEN_MS` = 450 ms) and lerps the up vector at constant distance, driven per frame by `_updateViewTween` in `_animate` (the `ViewHelper.update` tick is gone — `animating` never fires now). Views are Z-up: top = camera on +Z looking down (floor plan, ribweaver#281), front = camera on -Y looking along +Y (matches the axis bubbles), iso = the classic (1,-1,1) `resetView` direction; top/bottom get an axis-appropriate `up = +Y` so the view doesn't roll, everything else `up = +Z` (presets in `VIEW_PRESETS`). Works under both cameras (position/lookAt only — ortho zoom untouched). A pointerdown outside the gizmo rect or a wheel zoom cancels an in-flight tween so the user always wins. Python: `set_view(name, animate=True)` (validated against `_ALLOWED_VIEWS`, `animate=False` jumps instantly) → `set_view` WS message; `opts.animate === false` on the JS side. The ISO button is `tjsv-view-iso` in `template.html` (top-left corner of the 128 px gimbal area, shares the Home button styling + `--tjsv-anim-lift` shift). Transient like `set_camera` (not replayed on reconnect).

- **Camera pose API**: `get_camera()` / `set_camera(position=, target=, up=, fov=, zoom=)` — read/write the live camera pose over the socket. `get_camera()` is a request/response round-trip (requestId like `query_scene`) returning `{position, target, up, fov, zoom}` (`fov` is `None` while ortho is active; `zoom` is the framing control for ortho). `set_camera` applies only the provided fields, clamps `fov` to `[1, 179]`, and **explicitly re-orients via `camera.lookAt(target)`** — `ViewerControls.update()` deliberately never calls lookAt, so without it a position/target change would move the camera while it kept facing its old direction. Python validates eagerly (3-vectors, finite, `fov` in `(0, 180)`, `zoom > 0`). Intended workflow: orbit to a view by hand, `get_camera()`, paste into `set_camera(...)` to pin a scripted default. - **Move/rotate gizmo**: opt-in interactive transform manipulator, owned by the in-file `TransformGizmoController`, which wraps three.js `TransformControls` (reusing its drag/rotate/snap math) rather than hand-rolling a gizmo. The controller manages a `_primary` interactive gizmo (the click-select / `enable({id})` target, always present so the legacy `control`/`helper`/`object`/`objectId` surface keeps working as getters) **plus any number of pinned `_extra` gizmos** (`add_gizmo`), each its own `TransformControls` with its own axis constraint and base mode but all sharing the controller's modifier handling, snap settings, drag ghost, and report/change hooks. Per-target state (object, id, axes, ghost, snap origin, sized-plane set) lives on a small in-file `Gizmo` record. Enable from Python with `enable_move_gizmo(id=None, mode="translate", translate_snap=1.0, translate_snap_relative=False, rotate_snap_deg=15.0, click_select=True)` / `on_object_move(callback)`, or from JS via `viewer.enableMoveGizmo` / `viewer.attachMoveGizmo(object3D, id=null)` / `onObjectMove` / `onObjectChange` / `setGizmoMode` / `setGizmoAxes` / `setGizmoTranslateSnap` / `disableMoveGizmo`. Held **Alt** = rotate (locked at drag-start), held **Shift** = snap (translate grid / rotate degrees, sampled live) — but **Shift toggles snap relative to the gizmo's resting state**: a normal gizmo is free at rest so Shift *enables* snap, whereas a `snapDefault` gizmo snaps at rest so Shift *releases* it for free placement (same key, inverted; Shift dodges the macOS Ctrl-click-is-right-click trap). `_syncModifiers` computes `g.snapDefault ? !shiftKey : shiftKey` per gizmo and `_onDragChange` re-applies the resting snap at drag-start from the live step + last-seen Shift state (`this._shiftHeld`), so a `snapDefault` gizmo snaps from the first drag even with no key pressed and even if the snap step was set after the gizmo was pinned. Alt is a *momentary* override: it switches the live control to rotate while held and falls back to the caller-set base `mode` on release (it does not mutate `this.mode`), so an Alt tap can't clobber a `setGizmoMode('rotate')`. Target selection is both: `id=` attaches immediately, and `click_select` (default on) attaches by clicking any object (whole-object raycast; a drag is an orbit, not a select). **`viewer.attachMoveGizmo(object3D, id=null)`** is the JS-only escape hatch for an embedder: it attaches the gizmo to *any* `Object3D` (including a bare sentinel the viewer never tracked in `_objects`, which `enableMoveGizmo({id})` can't reach) and auto-enables the controller (modifiers, per-frame update loop, and move reporting all go live). The internal `attach()` ensures-enabled via a shared `_activate()` so a programmatic attach behaves like an interactive one. **Axis constraint**: `set_gizmo_axes(x=True, y=True, z=True)` (Python) / `viewer.setGizmoAxes({x,y,z}|null)` (JS) hides individual translate arrows / rotate rings (e.g. `{x:false,y:false,z:true}` for a Z-only rail) by driving `TransformControls.showX/Y/Z`; an axis is shown unless its key is explicitly `false` (omitted/`null` → all shown). It's additive (`_restyleGizmo()` never touches `showX/Y/Z`) and the primary's `detach()` resets to all-axes, so a constraint set for one target doesn't silently leak to the next attach — the Python state is re-sent on reconnect *after* the enable, and cleared on `disable_move_gizmo`. `set_gizmo_axes` targets the interactive gizmo; pinned gizmos get their constraint at `add_gizmo` time. **Multiple gizmos**: `add_gizmo(id, x=True, y=True, z=True, mode="translate", space="world", snap_default=False)` (Python) / `viewer.addGizmo(objectOrId, {axes, mode, id, space, snapDefault})` / `viewer.clearGizmos()` (JS) pins a *persistent* gizmo to an object, one per call, so several objects can each carry their own manipulator at once — the axis flags are the same `setGizmoAxes` semantics, so `x=False,y=False,z=True` is a 1-DOF rail, `x=True,y=True,z=False` is a 2-DOF in-plane slider (two arrows + the XY plane chip), and all-true is the full 3-DOF gizmo. `space` (validated against `_ALLOWED_GIZMO_SPACES` in Python) drives `TransformControls.setSpace`: `"world"` (default) keeps the handles world-axis-aligned, `"local"` orients them to the object's own rotation so the gizmo turns with a tilted object. `snap_default=True` flips the snap convention for that gizmo (snap is the resting state, Shift moves freely — see the modifier note above); the snap *step* still comes from the interactive gizmo's `translate_snap`/`rotate_snap_deg`, and `snap_default` is also accepted on `enable_move_gizmo`. See `examples/24_gizmo_dimensions.py`, which pins a world row and a rotated local row, all `snap_default=True`. Pinned gizmos report through the same `on_object_move` callback, are re-pinned on reconnect (each `add_gizmo` message re-`_activate()`s the subsystem, so no separate enable is needed), and are dropped by `clear_gizmos`, `disable_move_gizmo`, or a scene `clear` (the per-frame `update()` also prunes any whose target object left the scene). `on_object_move` only auto-enables the click-select interactive gizmo when **no** gizmo is configured (neither the interactive one nor any pinned one), so pinning then registering a callback doesn't draw an extra interactive gizmo. **Drag ghost**: on `dragging-changed` the controller drops a translucent clone (`__gizmoGhost`, opacity `GIZMO_GHOST_OPACITY`) of the dragged object at its grab-time world pose, parented to the scene root (so it stays put while the object moves), and removes + disposes it on release — the clone shares the source geometry but gets its own faint, depth-write-free materials and never raycasts. **Relative translation snap**: `enable_move_gizmo(translate_snap_relative=True)` / `enableMoveGizmo({translateSnapRelative:true})` / `viewer.setGizmoTranslateSnap(step, {relative:true})` quantises the drag *delta* from the grab-time position (captured on `dragging-changed`) instead of an absolute world grid — an item at `347` nudged a step lands at `447`, not on the nearest grid line. In relative mode the native (Shift-held) absolute `translationSnap` is suppressed and the quantise runs by hand inside `_onObjectChange` on **every** drag frame (always-on, not Shift-gated; only in translate mode); `setGizmoTranslateSnap(null)` disables snap entirely, and `{relative:false}` restores absolute grid snap. Rotation snap stays Shift-gated. **Per-frame change hook**: `viewer.onObjectChange(cb)` fires synchronously on every `objectChange` (each rendered drag frame, before the throttled report), payload `{object3D, id}`; the hook may mutate `object3D.position`/`.quaternion` and the change is reflected in the subsequent report. Ordering inside `_onObjectChange` is **relative-snap → change hooks → `_report`**, so both a hook and the report observe the snapped pose. Use it for live numeric readouts (the 30 Hz report is visibly jittery) without a WS round-trip; returns an unsubscribe fn. Drags report `{id, position, quaternion, scale, matrix, positionStart, quaternionStart, mode, phase}` back to `on_object_move` (throttled `"move"` ≤30 Hz + final `"end"`); `positionStart`/`quaternionStart` (Python: `position_start`/`quaternion_start`) carry the grab-time pose captured on drag-start, so a consumer can reconstruct the original world matrix from the payload, and `mode` is the **effective** mode of the drag read off the live control (`"translate"`/`"rotate"`/`"scale"`) — during an Alt momentary rotate override it reports `"rotate"` while the base mode stays translate, so consumers that branch translate-vs-rotate must use this field, not the mode they configured (issue #84: without it, Alt rotate-drags were silently discarded by embedders). Enabled state replays on reconnect. Orbit is suppressed during a handle drag via `dragging-changed` (like the clip gizmo); the gizmo follows the active camera across persp↔ortho switches (`control.camera` synced each frame) and lives in the scene (not `_objects`) so it survives `clear` and auto-detaches if its target is deleted. **Framing exclusion** (issue #144): every gizmo helper root (primary + pinned extras) is tagged `userData.isGizmoHelper` at construction and skipped by `_collectFrameableBounds()` — the TransformControls drag plane is a ~±50k mesh with an invisible *material* but a visible object, so frameAll/Home used to union it and fly the camera ~250 km out. The clip gizmos were already excluded there via `_isClipHelper`, and `updateSceneBounds()` (near/far fit) only iterates `_objects` + opted-in overlays, which never contain gizmo helpers, so it needed no change. The transient drag ghost (`__gizmoGhost`) is deliberately *not* excluded — it sits at the dragged object's own grab-time pose, so it can't inflate bounds beyond real content. **Restyle**: `_restyleGizmo(g)` runs per gizmo every frame. `TransformControls` re-themes its handles every frame from a cached `material._color`/`_opacity`, so the controller overwrites that cache each frame for a refined palette (colours cached per hex to avoid per-frame allocation); geometry tweaks persist because the lib bakes each handle's offset into its geometry at setup (`applyMatrix4`) and thereafter only re-*transforms* handles (sets `handle.position = worldPosition`, scale-to-screen). Translate plane chips are enlarged about their own centroid **and pushed outward by `GIZMO_PLANE_MARGIN`** along their offset direction (so the three chips leave a gap around the gizmo centre instead of crowding the origin) — applied to the visible chip *and* its invisible picker both, so the hit area tracks the visual. Each chip is also **flattened to a quad**: the stock chip is a thin `BoxGeometry` (depth `0.01`), which reads as a 3D slab and whose edge outline draws a back rectangle too — so the resize collapses the chip's thinnest bbox axis (detected, not hardcoded, because the box is pre-rotated/baked) to zero. A bright edge outline is added as a child of the **visible** chip only: the picker discriminator is the parent group's visibility (`o.parent.visible === false`), **not** the material's `visible` flag — `matInvisible` is opacity-based (`visible:true`), so a stale `m.visible === false` test let outlines leak onto picker chips, and a raycastable outline on a picker is hit before the chip and reports an empty `axis`, silently breaking plane-chip dragging. Both `_restyleGizmo(g)` and `_refineHandles(g)` are thin wrappers over the in-file free functions `restyleGizmoHelper(helper, sizedPlanes)` / `refineGizmoHandles(control)`, which the clipping tool's two gizmos reuse for the same refined look (see the Clipping plane entry). **`_refineHandles(g)`** is a separate *one-time* structural pass (per gizmo, at construction — distinct from the per-frame `_restyleGizmo`): (1) it slims the rotate gizmo to just the three coloured axis rings by removing the bulky outer screen-space ring (`E`), the gray full-circle backdrop (`XYZE`), and the gray `AXIS` helper line from the rotate gizmo/picker/helper groups; (2) it swaps each translate arrow's flat unlit `MeshBasicMaterial` for a lit `MeshStandardMaterial` (axis colour, small emissive floor, `depthTest/Write:false`, `toneMapped:false`) so scene lighting/environment give the cones real depth — the lib's per-frame re-theme/highlight only touch `.color`/`.opacity`, which `MeshStandardMaterial` supports, so they keep working; (3) it **slims the translate pickers** — hover resolves closest-intersection-wins across all pickers, and the stock arrow pickers are fat cone volumes hugging each axis (radius 0.2 vs 0.04 for the visible cone), so from any 3/4 view they bulged in front of the flat plane chips and stole roughly half of each chip's visible parallelogram (the chip's own enlarged picker was unreachable there — careful mousing on the blue XY chip grabbed the X arrow instead). Each arrow picker's two radial (non-axis) geometry dims are scaled by `GIZMO_ARROW_PICKER_SLIM` (0.4 → radius 0.08, still ~2× the visible cone's hit slop) and the centre free-move `XYZ` octahedron by `GIZMO_CENTER_PICKER_SCALE` (0.6); the axis passes through the baked geometry's radial origin so a plain `geometry.scale` keeps them centred (guarded one-time via `userData.__slimPicker`). Verified with a synthetic pointer-move grid scan reading `control.axis`: the chip's reported hover area now covers the parallelogram, and arrows remain hittable along their length/tips. No runtime UI/keys of its own (distinct from the clip gizmo's `C` panel).

### Animation: Two Approaches
**Frame-based (simple, familiar):** Build frames as Python dicts — good for small animations and prototyping.
**Binary channels (fast):** Use `add_channel()` / convenience wrappers for large animations (100+ objects × 1000+ frames). Data is packed as typed arrays, transferred via HTTP, and applied with zero-copy TypedArray views in JS.

Binary channel API:
- `animation.set_frame_times(times)` — numpy array of frame times
- `animation.set_transform_data(object_ids, data)` — (n_frames, n_objects, 16) float32
- `animation.set_draw_range_data(object_ids, data)` — (n_frames, n_objects) float32
- `animation.set_clip_time_data(object_ids, data)` — (n_frames, n_objects) float32
- `animation.set_point_time_data(object_ids, data)` — (n_frames, n_objects) float32 point-cloud scrub times
- `animation.add_channel(name, ids, data, dtype, stride, metadata)` — generic channel

Supported channel types: `transforms` (stride=16), `draw_ranges`, `colors`, `visibility`, `opacity`, `clip_times`, `point_times`
Supported dtypes: `float64`, `float32`, `uint32`, `uint8`. The `draw_ranges`, `clip_times`, and `point_times` convenience setters pack **float64**: their values are fractions of total arc length / absolute seconds, where one float32 ulp is ~0.5 mm of frontier position on a multi-km toolpath or ~16 ms at t=160,000 s (knots wobble, ms-spaced keys collapse to equal values). `transforms` and camera channels stay float32 (mm-scale values, and 2x the bytes would be real memory there). The packer sorts channels by element size descending so the float64 block leads the payload and every channel's byte offset is aligned to its element size; the viewer copies misaligned hand-packed `handleMessage` payloads instead of throwing.
Indexed colors: `dtype="uint8"` + `metadata={"colormap": [0x44AA44, 0xFF3333]}`

Binary channels and Frame-based JSON can coexist. A binary channel supersedes the same-named Frame field.

**Interpolation (per-channel):** Every *binary* animation channel carries its own interpolation mode — `"linear"` (lerp/slerp between keyframes) or `"hold"` (keep the previous keyframe's value until the next one hits). **Every channel defaults to `"linear"`** — opt out per channel with `add_channel(interpolation="hold")` or via the convenience setters (`set_transform_data`, `set_draw_range_data`, `set_clip_time_data`, `set_point_time_data`, `set_camera_target`, `set_camera_position`). Translations lerp, rotations slerp, float channels lerp element-wise, and `colors` lerps hex values in 8-bit RGB space (works for direct hex and colormap-indexed `uint8`). The `visibility` channel is a boolean and always left-holds regardless of the setting — a "linear bool" has no meaningful interpretation; the setting is accepted and validated but has no effect on that channel. **JSON `Frame` objects do not carry interpolation metadata and always interpolate linearly** between consecutive frames (visibility aside) — if you need hold behavior, use a binary channel. There is no Animation-wide knob — it was redundant with per-channel. Linear playback lets producers sample at the signal's bandwidth (e.g. 10 Hz) and still get smooth 60 fps. See `examples/17_animation_interpolation.py` for a HOLD ⇄ LINEAR comparison on the same tumbling capsules.

**Interpolation is per-object, not kinematic** (issue #162): between two keyframes each object's matrix is decomposed and interpolated *independently* (`lerpMatrixInto`: position lerp, quaternion slerp, scale lerp), with no knowledge of any parent/child relationship or of the mechanism the objects represent. Between keys the render is therefore **not a kinematically consistent pose** for an articulated chain — a link whose geometry sits at an offset inside its group traces an **arc** (`lerp(origin) + slerp(R)·offset`), while a group animated with pure positions (a tool-mounted marker, a TCP node) traces the **chord** between the same two keys; the two visibly disagree in between, and no per-channel setting fixes it because each object is honest about its own two keys. Measured on a 512-station calibration path: p99 tip deviation **72.6 mm** at a nozzle whose group origin is **583 mm** from the TCP, while the TCP group itself stayed on-line to 3e-12 mm. On keys, every object is exact. So when exactness *between* keys matters (a robot chain, a tool riding a link), the sender must **densify keyframes** to the accuracy it needs, or use `interpolation="hold"` to step rather than smear (the third option for a single tool body is `set_follow_path`, which recomputes the pose from the real path each render tick instead of interpolating keyframes).

**Non-finite matrices hold the last good pose** (issue #162): a single NaN/Inf element anywhere in a 4x4 poisons `matrixWorld` for the whole subtree — every vertex lands at NaN clip space and three.js drops the object outright, so a link silently vanishes mid-playback with no diagnostic. Every matrix write coming off the wire is therefore checked by the free functions `matrixElementsFinite`/`setObjectMatrixChecked`/`setObjectMatrix4Checked`: the `transforms` channel (both the step and the interpolated path — NaN propagates through decompose/lerp/slerp/compose, so checking the composed result catches a bad keyframe on either side), the JSON `Frame.transforms` path, and `update_transform` (`set_matrix`/`batch_update`, whose loose `position`/`rotation`/`quaternion`/`scale` form is guarded too). A bad matrix is dropped and the object simply keeps its previous pose, with **one `console.warn` per object id** (`userData.__warnedNonFiniteMatrix`) — a NaN keyframe is usually a whole bad channel, and warning per frame would flood the console at 60fps. Cost is 16 `Number.isFinite` calls per *applied* matrix (only the keyframe pair being applied this frame): ~6.5 µs/frame for the 520-object stress example (`examples/10_animation_stress_test.py`), ~0.04% of a 16.7 ms frame and an order of magnitude under the decompose/slerp/compose the linear path already runs per object.
