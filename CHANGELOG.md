# Changelog

## 0.0.40

### Point clouds: per-point time windows (#79)

- **`add_points(..., birth_times=, removal_times=)` — per-point `[birth, removal)` lifetimes filtered in the vertex shader against a scrubbable per-cloud time.** A point is visible while `birth_time <= t < removal_time`; culled points get `gl_Position` shoved outside the clip volume (clipped pre-raster, zero fragment cost — Potree's GPS-time-filter trick, patched into the stock `PointsMaterial` via `onBeforeCompile` + a `customProgramCacheKey` per attribute combination). This expresses **out-of-order** appearance/removal that the `draw_range` buffer-prefix reveal cannot (material removal is not a prefix). NaN/±inf ends mean unbounded (NaN birth = always existed, NaN removal = never removed; mapped to ±FLT_MAX Python-side because GLSL NaN compares are undefined). The scrub time starts at 0 and is driven by `set_points_time(id, t)` (streaming; validates finite) or the new **`point_times` binary animation channel** (`Animation.set_point_time_data`, `Frame(point_times=...)` on the JSON path) so the standard animation slider scrubs points in and out; the uniform object is shared by reference into every program compiled from the material (including the EDL depth pre-pass), so scrubbing touches no material state. The `add_points_binary` loader validates the full expected payload size before parsing (a truncated payload previously zero-padded the trailing time blocks silently).

### Point clouds: streamed octree LOD (#79)

- **`add_points(..., lod=True | {node_capacity, point_budget, refine_pixels, max_depth, seed, size_boost_max, grid})` — opt-in Potree-style octree LOD for clouds beyond one draw call (design + prior-art rationale in `plans/points-octree-lod.md`).** Python builds an **additive sampled octree** (`points_lod.py`): every node owns a seeded pseudo-random sample of its cube, **time-stratified** over birth/removal times so the time filter thins every LOD level uniformly instead of punching patchy holes; children add detail, no point is stored twice, and every rendered point at every LOD is a real point carrying its true attributes (sampled real points beat aggregated rollups precisely because a merged voxel would fabricate a lifetime belonging to no real point). Per-node vertex order is Morton-sorted then shuffled in 128-point batches (Schütz 2021, up to ~4× raw GL_POINTS throughput). Transport is **pull-based**: one WS header + a 40 B/node binary hierarchy blob (bounds, count, `[min birth, max removal)` time bounds, BFS `first_child`/`child_mask` topology), then the viewer fetches node payloads on demand (`GET <sidecar>/points_lod_<uuid>/<i>`) from **lazy callable blob-store providers** that quantize + pack a numpy slice per request — nothing is materialized up front, and the Python process must stay alive to serve refinement. Node payloads are normalized **int16 xyz** over the node cube (dequantized free via normalized attributes + the node's center/scale transform; ints stay GPU-resident) + u8 rgb + f32 times. The viewer runs a per-frame priority traversal (max-heap on projected node size): refine while ≥ `refine_pixels` (default 12 px), stop adding at `point_budget` (default 1.5M; an over-budget node skips its subtree but smaller branches keep filling), ≤6 concurrent fetches, LRU eviction past ~3× budget, per-node frustum culling via explicit bounds, and **per-node time culling** (a node whose window misses the scrub time is neither drawn nor fetched). Coarse nodes draw slightly fatter points (√2/level, capped `size_boost_max`, default 2×). `set_points_time`/`point_times` drive LOD clouds identically to flat ones; `set_draw_range` is a documented no-op on LOD clouds (buffer order is per-node Morton — the viewer warns once and points at the time window); `frame_object`, `F`/Home framing and near/far fitting honour the cloud's full root-cube extent before any node has streamed. `lod={}` means all-defaults (explicit None/False check, not truthiness). Octree build: one global time-sorted candidate order + boolean-mask partitioning (~1.2–1.7M pts/s).
- **Grid fast-path for lattice-aligned clouds** — `lod={"grid": {"spacing": pitch}}` builds the same octree from one global uint64 Morton code + one sort (`build_points_octree_grid`): every octree cell at every level is a contiguous range of the sorted array, octants split by `searchsorted`, no per-node re-partition or sort — ~4× faster than the float builder at 8M lattice points (1.1 s vs 4.4 s) and flat as N grows, with identical node structure. Sampling on this path is spatial (strided over Morton order); `strat_times` is accepted but ignored — carve removal times are spatially correlated, and skipping the time sort keeps the build bit-reproducible. An **external producer** (e.g. a Rust kernel) can pre-supply `"codes"`/`"order"`/`"n_bits"` (global Morton codes + their ascending sort permutation) and the builder skips its two super-linear stages; the bit-exact contract is `docs/points-lod-grid-api.md` with `grid_morton_codes()` as the Python reference, and tests assert byte-identical octrees between the internal and producer-supplied paths. Gated on the caller's grid promise (the bit-slice octant test only matches the float `pos > centre` test for cell-centred points).
- New demo `examples/27_points_octree_lod.py` — point count tunable from the command line (default 2M): a wavy sheet streams node detail on demand under the budget while a diagonal build front adds points and a trailing erosion front removes them out of buffer order via the animation slider; a NaN-removal "bedrock" band persists. The script stays running to serve nodes (Ctrl+C to quit).

- **`set_points_lod_options(id, point_budget=, refine_pixels=, size_boost_max=)` — retune a streamed cloud's traversal at runtime, no re-upload (#87).** The three knobs were only settable at `add_points(lod=...)` time, so densifying a 27M-point carve view meant minutes of re-upload + octree rebuild to change two scalars the traversal reads fresh every frame anyway. The new message lands on the live runtime state (budget and refine threshold apply on the next traversal frame; the eviction limit follows the budget), and a `size_boost_max` change also re-derives the point size on every already-streamed node material. Fields left `None` are unchanged; values are transient viewer state (a browser refresh reverts to the add-time options).

### Eye-dome lighting

- **EDL auto-enables the first time a point cloud (flat or LOD) is added** — unlit point quads read as a washed-out sheet without a depth cue. The auto-enable is suppressed once the user *pins* the EDL state (`Shift+D`, `set_depth_cue(edl=...)`, or the new `set_edl(...)`) — **including an explicit OFF**, so `set_edl(False)` sticks even for point clouds. `set_depth_cue` grows `edl_strength` / `edl_radius` (live shader re-tuning without toggling), and the focused **`set_edl(enabled=True, strength=None, radius=None)`** covers the common "switch on depth shading for a cloud" case; tuning values survive composer rebuilds and can be set before the composer exists. Mild behavior change: existing point-cloud scripts now open with EDL on unless they pin it off.

### Camera

- **`get_camera()` / `set_camera(position=, target=, up=, fov=, zoom=)` — read/write the live camera pose over the socket.** `get_camera()` round-trips `{position, target, up, fov, zoom}` (requestId mechanism like `query_scene`; `fov` is `None` while ortho is active, `zoom` is the ortho framing control so round-trips are faithful under both cameras). `set_camera` applies only the provided fields, clamps `fov` to `[1, 179]`, validates eagerly Python-side (3-vectors, finite, `zoom > 0`), and **explicitly re-orients via `camera.lookAt(target)`** — `ViewerControls.update()` deliberately never calls lookAt, so without it the camera moved while still facing its old direction. Intended workflow: orbit to a view by hand, `get_camera()`, paste into `set_camera(...)` to pin a scripted default. Pose is transient (not replayed on reconnect).
- **`frame_object(id)`** — fit the camera to one object's bounding box (the programmatic double-click), LOD-root-box aware.

### Follow-path track

- **`set_follow_path(id, times, positions, axes)` — object rides a timed 5-axis path with its pose computed per render tick from the real path.** Animation `transforms` frames may sample a long timeline coarsely (e.g. 10 Hz), which aliases a fast tool on a detailed toolpath; a follow-path track instead binary-searches the full-resolution path at the current animation clock every rendered frame — tip position lerped, tool axis nlerped, minimal rotation of the object's local `+z` onto the axis, the object's own scale preserved. Payload is binary float32 `[t,px,py,pz,ax,ay,az]` rows (K≥2, non-decreasing times, validated Python-side) over the blob sidecar. Tracks are per-id (re-send replaces), dropped on `delete`/`clear`, and a follow-path object is the **preferred `T`-key camera-tracking target** (picked before the transform-channel name hints).
### Move/rotate gizmo

- **Gizmo reports now carry the *effective* drag mode** (`mode: "translate" | "rotate" | "scale"`, Python: `move["mode"]`), read off the live `TransformControls` — so an **Alt** momentary rotate override is observable: the report says `"rotate"` even though the gizmo's base mode is still translate. Previously the payload had no mode field at all, so an embedder whose handler must interpret the drag per mode (position-only vs orientation) could only branch on the base mode, ran the translate branch on an Alt rotate-drag (position unchanged → no-op), and the rotation was silently wiped on drag-end (#84). Branch on the payload's `mode`, not the mode you configured.

### Playback

- **Pace smoothing (#97): the playhead advances by a short EMA of the wall-clock frame delta instead of the raw delta.** Advancing by raw `deltaTime * speed` passed every render-cost fluctuation straight into playback velocity — on heavy scenes (tube frontier morph, LOD churn, growing geometry) the frame cost varies continuously, so playback visibly accelerated/decelerated in proportion, amplified by the speed multiplier (a single 4x-slow frame teleported the playhead 4x further). The delta is now clamped (3x the running average, so a stalled frame or a background tab can't teleport the playhead or poison the average) and EMA-smoothed (~10-frame window) before the speed multiplier applies: velocity stays visually constant while still tracking real time on average. Position mapping was always exact — only the advance *rate* was noisy.
- **Uniform-dt fast path honours a nonzero start time (#96).** `_getFrameAtTime`'s uniformly-spaced fast path computed the frame index as `time / uniformDt`, which is only right when the timeline starts at 0 — a uniform timeline starting at e.g. `t=100000` clamped every lookup to the last frame (seeking anywhere showed the end state). Now `(time - frames[0].time) / uniformDt`. The non-uniform binary-search path was unaffected.

### Toolpaths

- **Travel-move rendering (#88): `add_toolpath(..., travel="line", travel_color=...)` + a line-segments polyline primitive.** A real G-code path has many disjoint travel episodes (thousands in large-format files); the old options were one object per episode or a whole-path line hidden inside the opaque bead — occlusion as a side effect, broken by `opacity < 1` and LOD thinning. Now: `add_polyline(..., segments=True)` renders disjoint edges (`THREE.LineSegments`, consecutive point pairs, one draw call, no false connectors; even point count required, native path implied, never pickable), and `add_toolpath(travel="line")` builds the travel line from the zero-width stretches it already computes — every spine edge not interior to an extrusion run, so each hop meets the bead ends — and wires it into the group's draw-range distribution by contract (`travelId` + ascending per-edge end fractions in `register_toolpath_group`; the group reveal binary-searches them), so `set_draw_range` and the `draw_ranges` channel advance beads and travel hops in exact lockstep. Also documented: one `draw_ranges` channel can drive multiple objects of different types in lockstep (`set_draw_range_data([tube_id, line_id], data)`). `examples/15_toolpath_interrupted.py` now shows the travel line.

### Embedding

- **JS camera / pick / controls surface for embedders (#77)** — no more reaching into `viewer._camera` / `_controls` / `_renderer`: `viewer.getCameraPose()` → `{position, target, up, fov, zoom}`; `viewer.setCameraPose({...})` (partial, vectors as `{x,y,z}` or `[x,y,z]`, explicitly re-orients at the target; now also the implementation behind the `set_camera` WS case so the two can't drift); `viewer.frameBox(min, max, margin=1.5)` fits the camera to a world AABB; `viewer.pick(clientX, clientY, {pointsThreshold, ids})` raycasts meshes + point clouds from viewport coordinates, skips hidden subtrees, resolves the top-level tracked id by walking ancestors, and returns `{point, objectId, distance, object3D}` of the nearest hit or `null` (lines stay on the dedicated arc-length `enablePolylinePicking` path); `viewer.setControlsEnabled(bool)` suppresses orbiting while an embedder drags its own handle.
- **Animation transport, object handles, overlays, and the status chip for embedders (#74, #75, #76, #78).** `viewer.seekAnimationTime(s)` / `getAnimationState()` / `setAnimationPlaying(bool)` / `setAnimationSpeed(mult)` / `onAnimationTime(cb)` expose the viewer's one animation clock (the same one driving `draw_range` reveals, follow-path tracks, and the native transport UI) — the hook fires with the full state on every applied frame and on play/pause flips, so a docked scrubber/graph needs no rAF poll. `viewer.getObject(id)` hands out the loaded `THREE.Object3D` as a documented styling/raycast escape hatch, and `handleMessage()` now **returns** the reply payload for query messages (`list_objects`/`query_scene`/`get_camera`) so no-WebSocket embeds get answers without a socket. `viewer.addOverlay(object3D, {id, includeInBounds})` / `removeOverlay(idOrObject)` mount embedder-owned live content (an animated cutter, a selection box, transient highlights) with defined semantics: excluded from framing/scene bounds by default (opt-in `includeInBounds`), untouched by scene `clear`, never disposed by the viewer. `viewer.setStatus(text, state)` drives the header chip (new `neutral` style), and `autoConnect: false` now defaults it to "Local data" instead of a forever-misleading "Waiting for Python...".

## 0.0.39

### Point clouds

- **`add_points(id, positions, colors=..., colormap=..., color=0xFFFFFF, size=2.0, size_attenuation=True, parent=None)` — GPU point cloud rendered as a single `THREE.Points` draw call.** For massive unconnected clouds (voxel fields, metrology/deviation clouds, LiDAR scans) where `add_polyline` would wrongly connect the points and one primitive per point is far too heavy. Positions (+ optional colors) ship over the binary HTTP channel like `add_polyline`, and per-point colours run through the same `_apply_colormap` path: a scalar `(N,)` array mapped via `colormap`/`cmin`/`cmax` (e.g. a signed-deviation heatmap), an `(N, 3)` RGB float array, or the flat `color` fallback when `colors=None` — a `colors` length that doesn't match the point count raises `ValueError` Python-side instead of shipping a misaligned blob (which rendered as NaN vertex colours with no error). The viewer builds a native `THREE.PointsMaterial` (chosen over a custom shader for its viewport-aware size attenuation, and because it composes with the existing `set_color` / disposal / fog-scoping paths for free): `size` is the base point size in px, `size_attenuation=True` (default) shrinks points with distance, `False` draws a constant pixel size — and falsy values are honoured (`color=0x000000` renders black, `size=0` stays 0; the option plumbing uses `??`, not `||`). Supports `set_draw_range` and the binary `draw_ranges` animation channel (reveals the leading `frac*N` points of the buffer — order the points along a toolpath for a cheap material-removal animation), and point clouds join the EDL line layer so eye-dome lighting sculpts them too. Flat `THREE.Points` covers ≤~10M points comfortably; octree/Potree LOD for larger clouds is a separate later tier, and picking is not wired for points (the arc-length `PolylinePickController` is spine-based). New demo `examples/25_point_cloud.py` — a dense (~160k-point) machined "cut surface" sampled along a serpentine raster, coloured by signed deviation (turbo), revealed by a `draw_ranges` sweep like a material-removal pass. Regression covered by `tests/test_protocol.py` (header type, parent, vertex-colour flag, scalar→colormap, RGB payload, size/attenuation, bad-shape and length-mismatch `ValueError`) and `tests/test_browser.py` (cloud lands as `type: "Points"`, `set_draw_range` applies end-to-end, flat black honoured).

### Swept tool body (5-axis)

- **`add_swept_tool(id, positions, axes, profile, colors=..., sections=16, color=..., opacity=1.0, metalness=..., roughness=...)` — swept *oriented* tool-body tube for 5-axis toolpaths.** The crux vs `add_parametric_tube`: it **decouples the extrusion axis from the path tangent**. At each station `k` the `(height_along_axis, radius)` `profile` (M×2, revolved into rings of `sections` verts) is lofted about the **tool axis** `axes[k]` (unit, tip→holder — generally *not* the path tangent), centred at `positions[k]`, and consecutive stations are connected into a swept surface — the swept shank/holder of a tilting tool, which reveals reorientation-rate "wrist speed" and tool-body collisions the cutting-tip envelope can't. Geometry is built client-side by the in-file free function `buildSweptToolGeometry`: per densified profile level a ring is lofted along the path (per-level swept tube), straight profile runs are densified in height so a sparse profile still sweeps a continuous wall, revolution end caps close the first/last station, and a per-station constant-up frame (V anchored to +Z, +X fallback near-vertical) keeps rings from twisting. The start cap is emitted **before** the side loft so the origin end is closed from the very first `draw_range` frame (only the far/frontier cap appears last), and the end-cap fan allocates exactly `(sections−2)*3` indices so `totalIndexCount` is exact with no trailing zero-index degenerate triangles. Per-station `colors` are packed `uint32 0x00RRGGBB` (like the tube), linearly interpolated along the path; `MeshStandardMaterial` (DoubleSide, `opacity<1` → translucent so the part shows through for collision reads), with a flat `color=0x000000` honoured. Index order is station-major so `set_draw_range`/`draw_ranges` reveals the body along the path — and the binary `draw_ranges` animation-channel apply (a *separate* code path from the `set_draw_range` message, which had silently drifted out of sync) now handles swept tools and point clouds, with a regression test seeking mid-animation and asserting both draw ranges advance. The linear loft can pinch/self-intersect on the inside of a sharp axis swing — accepted (faithful surface, not a boolean solid); tool-body picking and LOD are not wired for this primitive. New demo `examples/26_swept_tool.py` — a tilting ball+shank tool lofted along a contact path, coloured by reorientation rate (blue calm → red fast wrist motion), with a `draw_ranges` animation advancing the tool along the path.

### Clipping tool

- **Refined gizmos + a drag-the-plane-along-its-normal handle.** The clipping tool now wears the same refined gizmo styling as the move/rotate gizmo, via a pair of in-file free functions extracted from `TransformGizmoController`: `refineGizmoHandles(control)` (one-time: strip the bulky `E`/`XYZE`/`AXIS` rotate handles, swap translate cones to a lit `MeshStandardMaterial`) and `restyleGizmoHelper(helper, sizedPlanes)` (per-frame palette re-theme). `_refineHandles`/`_restyleGizmo` are now thin wrappers over these, so the move gizmo and the clip gizmos share one implementation and can't drift. The clip **rotate** gizmo (`_clipGizmo`) is slimmed to just the three coloured axis rings, and a new **normal-slide** gizmo (`_clipMoveGizmo` — a local-space, Z-only/`showX=showY=false` translate handle with a shaded cone whose arrow follows the current plane normal) lets you drag the plane along its normal; previously plane movement was slider / arrow-keys only (both still work, as does the V-key normal-snap). Both gizmos ride the same `_clipAnchor`, report through one `_syncClipFromGizmo` handler (normal from the anchor orientation, distance from `position·normal`), enable/hide together with the panel, are restyled each frame from `_animate`, and follow the camera across persp↔ortho switches. Also in this batch: the clipping-panel slider range is bounded to user content. Regression covered by `tests/test_browser.py::test_clip_tool_has_refined_rotate_and_slide_gizmos` (both gizmos come up with the panel and go away with it).

### Embedding

- **`viewer.handleMessage(data)` — public, WS-decoupled control-message entry point.** The viewer already rendered fine with no WebSocket (`autoConnect: false`), but the control-message dispatch was an inline `onmessage` closure inside `connect()`, bound to a live socket — so driving the viewer from local/static data required monkeypatching `window.WebSocket`. The entire control-message switch moved verbatim into a public async `handleMessage(data)` method; `connect()`'s `onmessage` now only parses the WS frame (plus the large-frame warning) and delegates. An embedder can construct `new ThreeJSViewer(container, { autoConnect: false })` and feed messages straight in (`viewer.handleMessage({ type: 'add_points_binary', id, blob_url, ... })`) with no `websockets` server — binary payloads still load over HTTP (static files or in-page `Blob` object URLs) exactly as under the socket transport; only the dispatch is decoupled. The two query handlers that answer back (`list_objects`, `query_scene`) route through a guarded `_reply(payload)` that no-ops when no socket is connected, so query messages are safe to dispatch in static mode. The wire protocol, the Python client, and connected-socket behaviour are unchanged. Regression covered by `tests/test_browser.py::test_handle_message_dispatches_without_websocket`.

## 0.0.38

### Move / rotate gizmo: multiple pinned gizmos

- **`add_gizmo(id, x=True, y=True, z=True, mode="translate", space="world", snap_default=False)` / `clear_gizmos()` (Python), `viewer.addGizmo(objectOrId, {axes, mode, id, space, snapDefault})` / `viewer.clearGizmos()` (JS) — pin any number of *persistent* gizmos, one per call, so several objects can each carry their own manipulator at once.** The controller now manages the `_primary` interactive gizmo (the click-select / `enable({id})` target; the legacy single-gizmo surface `control`/`helper`/`object`/`objectId` stays as getters) plus any number of pinned `_extra` gizmos, each its own `TransformControls` with its own axis constraint and base mode, all sharing the controller's modifier handling, snap settings, drag ghost, and report/change hooks — per-target state lives on a small in-file `Gizmo` record. The axis flags are the `setGizmoAxes` semantics, so `x=False, y=False, z=True` is a 1-DOF rail, `x=True, y=True, z=False` a 2-DOF in-plane slider (two arrows + the XY plane chip), and all-true the full 3-DOF gizmo. `space` (validated against `_ALLOWED_GIZMO_SPACES` in Python) drives `TransformControls.setSpace`: `"world"` (default) keeps the handles world-axis-aligned, `"local"` orients them to the object's own rotation so the gizmo turns with a tilted object. Pinned gizmos report through the same `on_object_move` callback, are re-pinned on reconnect (each `add_gizmo` message re-`_activate()`s the subsystem, so no separate enable is needed), and are dropped by `clear_gizmos`, `disable_move_gizmo`, or a scene `clear` (the per-frame `update()` also prunes any whose target object left the scene); `on_object_move` only auto-enables the click-select interactive gizmo when **no** gizmo is configured (neither the interactive one nor any pinned one), so pinning then registering a callback doesn't draw an extra one.
- **`snap_default=True` — snap as the resting state, Shift for free placement.** Shift toggles snap *relative to the gizmo's resting state*: a normal gizmo is free at rest so Shift enables snap, whereas a `snapDefault` gizmo snaps at rest and Shift releases it for free placement (same key, inverted; Shift dodges the macOS Ctrl-click-is-right-click trap). `_syncModifiers` computes `g.snapDefault ? !shiftKey : shiftKey` per gizmo and `_onDragChange` re-applies the resting snap at drag-start from the live step + last-seen Shift state (`this._shiftHeld`), so a `snapDefault` gizmo snaps from the first drag even with no key pressed and even if the snap step was set after the gizmo was pinned. The snap *step* still comes from the interactive gizmo's `translate_snap`/`rotate_snap_deg`; `snap_default` is also accepted on `enable_move_gizmo`.
- **Drag ghost.** On `dragging-changed` the controller drops a translucent clone (`__gizmoGhost`, opacity `GIZMO_GHOST_OPACITY`) of the dragged object at its grab-time world pose, parented to the scene root so it stays put while the object moves, and removes + disposes it on release — the clone shares the source geometry but gets its own faint, depth-write-free materials and never raycasts.
- **Visual refinements: flat margined plane chips, shaded cones, slim rotate rings.** Each translate plane chip — a thin `BoxGeometry` slab in stock `TransformControls`, which read as a 3D slab whose edge outline drew a back rectangle too — is flattened to a quad (its thinnest bbox axis collapsed to zero; detected, not hardcoded, because the box is pre-rotated/baked) and pushed outward by `GIZMO_PLANE_MARGIN` along its offset direction so the three chips leave a gap around the gizmo centre instead of crowding the origin — applied to the visible chip *and* its invisible picker so the hit area tracks the visual. Translate arrow cones swap their flat unlit `MeshBasicMaterial` for a lit `MeshStandardMaterial` (axis colour, small emissive floor, `depthTest/Write:false`, `toneMapped:false`) so scene lighting/environment give them real depth, and the rotate gizmo is slimmed to just the three coloured axis rings (the bulky outer screen-space `E` ring, the gray `XYZE` full-circle backdrop, and the gray `AXIS` helper line removed) — all in a one-time `_refineHandles` structural pass, distinct from the per-frame restyle.
- **Fix: plane-chip dragging was silently broken by outlines leaking onto picker chips.** The bright edge outline added to each chip discriminated pickers by `material.visible === false`, but `matInvisible` is opacity-based (`visible: true`) — so outlines landed on picker chips too, and a raycastable outline on a picker was hit before the chip and reported an empty `axis`. Pickers are now discriminated by the parent group's visibility (`o.parent.visible === false`), and the outline is added as a child of the visible chip only.
- New demo `examples/24_gizmo_dimensions.py` — six gizmos pinned at once in a 2×3 grid: columns are 1-DOF / 2-DOF / 3-DOF (a blue Z-only rail, a green XY-plane slider, an orange free cube), rows are orientation space — a back row of upright blocks with `space="world"` and a front row of *rotated* blocks with `space="local"` (the gizmo turns with the tilted object), all `snap_default=True`, releases reporting through one shared `on_object_move`. Regression covered by `tests/test_client.py` (`add_gizmo` payload / `space` validation / `clear_gizmos`) and `tests/test_browser.py` (multi-DOF constraints, arrow + plane drags from both sides, drag ghost, local space + refined handles).

## 0.0.37

### Move / rotate gizmo: relative snap + per-frame change hook

- **Relative translation snap — quantise the drag *delta* from the grab-time position instead of an absolute world grid.** The stock three.js `TransformControls.setTranslationSnap(step)` snaps to absolute world lines: an object at `x = 347 mm` nudged `60 mm` lands on `400 mm` (the nearest grid line), not `447 mm` (one step from where it was picked up) — which silently breaks "nudge by 100 mm" workflows. Opt in via `ViewerClient.enable_move_gizmo(..., translate_snap_relative=True)` / `viewer.enableMoveGizmo({translateSnapRelative: true})`, or change it at runtime with the new `viewer.setGizmoTranslateSnap(step, {relative})` (pass `null` to disable snap entirely, `{relative: false}` to restore absolute-grid snap). In relative mode the gizmo captures the object's position on `dragging-changed` (drag-start) as the snap origin, suppresses the native absolute `translationSnap`, and quantises `position − snapOrigin` by hand inside the `objectChange` handler — **on every drag frame and only in translate mode** (so it isn't Shift-gated like the absolute path; rotation snap stays Shift-gated and drag-relative as before). Wired through the `set_move_gizmo` WebSocket message (`translateSnapRelative`) and re-sent on reconnect.
- **`viewer.onObjectChange(cb)` — a per-frame hook that fires on every `objectChange`, synchronously, before the throttled `onObjectMove` report.** The existing `onObjectMove` / `transform_gizmo {phase:"move"}` report is throttled to 30 Hz, which is visibly jittery for a live numeric readout that must track the handle at monitor refresh. The new hook fires once per rendered drag frame with `{object3D, id}` and **may mutate `object3D.position` / `.quaternion`** — the mutation is reflected in the subsequent report. The handler's ordering contract is **relative-snap → change hooks → report**, so a hook (and the report) always observe the already-snapped pose. Returns an unsubscribe function; JS-only (no WS round-trip by design, since a consumer's per-frame decompose typically needs client-only state like a grab-time parent-world matrix).

## 0.0.34

### Parametric tubes: sharp corners, layer-up reversals, exact retraces

- **Miter stretch now follows the actual turn plane (directional miter).** The per-corner miter used to scale only the cross-section's U (width) axis — exact for horizontal turns under the constant-up frame, but actively wrong for turns in a *vertical* plane: every layer-change elbow inflated the bead **sideways** by 1/cos(half-turn) (measured 1.40× lateral "wings"/barbs at the ends of an 8-layer wall — the "torn cardboard" look). `computeMiterFrames` now emits stride-3 miter data `[scale, mu, mv]` per spine point: the world-space turn direction `m = outDir − inDir` (exactly perpendicular to the bisector tangent, so it lies in the section plane) projected onto the section's U/V axes. The ring writers stretch the *anchored* section offset (height-anchor `vOff` included) by `scale` along `(mu, mv)` about the spine point — exactly the projection of each leg's ring onto the joint's bisector plane whenever the turn plane contains the up vector or is perpendicular to it (horizontal turns and vertical elbows — every turn a layer-by-layer toolpath makes; for a *skew* turn plane the constant-up frame carries a twist relative to the hinge frame and the stretched ring approximates the leg projections, still strictly closer than the old u-axis-only scale, and the mesh stays watertight either way). Horizontal turns reduce bit-for-bit to the old u-scale behaviour (`mu=±1, mv=0`); vertical elbows now stretch along V instead of flaring sideways. The hairpin U-flip sweep negates the stored `mu` when it flips a ring's U so every later consumer (draw_range frontier morph, end-cap rewrite) keeps the world-space miter direction; the frontier morph lerps the scale and blends the direction sign-aligned (axes, not vectors), treating a straight ring's placeholder direction as "use the other endpoint's".
- **Frames freeze across near-vertical riser runs (no more crumple knots).** A tangent within ~8° of vertical (`|T·up| > 0.99`) used to switch the V seed to the fallback axis ring-by-ring, planting frames ~90–135° away from their neighbours — on a densely-sampled layer riser every interior sample tripped it and the bead crumpled into a knot at every layer change. `computeMiterFrames` now records the in-cone runs and, in a post-pass, copies the nearest out-of-cone neighbour's frame across each run (entry frame for the first half, exit frame for the second half; lead-in/lead-out runs take the one available side). The hand-off mid-run where entry and exit U are anti-parallel is reconciled by the existing hairpin U-flip sweep — that covers the same-heading and exact-reversal hops that dominate real toolpaths; a *non-zero-width* riser whose plan heading changes across the hop keeps one twisted quad band at the mid-run hand-off (known residual, still far better than the per-ring crumple it replaces; zero-width travel risers are unaffected — their rings are degenerate points). Frozen rings keep their own bisector tangent (caps and morph read `tangents`) and get miter scale 1 — their section plane is already skewed by design, so a miter on top would be incoherent. A spine that is vertical end-to-end keeps the plain fallback frames (consistent, no jump within the run).
- **Bead miter limit lowered 4 → 2 (`TUBE_MITER_LIMIT`): turns sharper than 120° now bevel instead of spiking.** 4 is the SVG default for thin strokes; for squat bead solids a 150° turn produced a 3.86× flat blade with screen area comparable to both legs combined (and a width-peak at the corner multiplied it to ~7× leg width). At the limit of 2, ≤90° corners are untouched (1.41×), turns up to (just under) 120° keep their miter, and anything sharper drops to a compact bevel — strictly no worse than an unmitered joint at corners where the bisector frame is ill-defined anyway. An *exactly*-120° corner sits on the gate boundary (`cosHalf < 1/2`, strict): float rounding of the spine decides miter-or-bevel per corner, so don't rely on the boundary angle itself (the regression test probes 119°/150°, well clear of it).
- **Exact retraces (A→B→A) no longer z-fight: deposition-order bias + a tighter near-plane fit.** A retrace builds two *coincident* surfaces whose depth ties broke per-pixel, per-frame — violent shimmer under camera motion (measured 3.1%/step interior pixel flips under a 5° sweep, ~10× baseline) and a static forward-colour sawtooth breaking through the return leg. Two composed fixes: (1) `TUBE_DEPOSITION_BIAS = 1e-3` — each ring's cross-section is scaled up by `1 + 1e-3·idx/(total−1)`, applied to the decoded width/height arrays before the build, the LOD worker init, and the collapse offload. The scaling is about each ring's *anchored section centre*: the per-ring anchor offset (`vOffs`) is captured from the heights **before** the bias and plumbed through both threads — recomputing it from the biased heights would cancel the bias exactly on the anchored face, leaving an `anchor="top"` retrace still z-fighting on its top surface (the face seen from above, in the nozzle-tip-toolpath mode; covered by a dedicated regression test). The ramp index runs over the **whole toolpath**: `add_toolpath` splits at travel moves into segment tubes and threads the global ramp through `bias_index_offset`/`bias_index_total` on `add_parametric_tube`, so the realistic deposit→travel→retrace case nests across the split too. The later-deposited leg nests *outside* the earlier one — exactly so at full resolution and at every LOD-kept ring (between kept rings, LOD's chordal error can locally exceed the ≤0.1% bias for curved or varying-width retraces) — and the visible surface is deterministically the last bead laid (multiplicative, so zero-width travel segments stay exactly zero; ≤0.1% size error is far below visibility and the 4% strand-collapse tolerance). (2) The perspective near-plane fit no longer collapses to its 0.001 floor whenever the camera is within 1.5 bounding-sphere radii of the scene — `updateNearFar` now fits `near = max(0.001, (dist − radius)·0.5)` (nothing can sit closer than the sphere surface; the 0.5 keeps 2× clearance for bounds-recompute lag), which in a typical content-filling framing buys ~3 orders of magnitude of depth precision — the bias separation went from 0.1–0.3 depth quanta (invisible to the z-buffer) to >100. Because the tighter fit trusts the cached scene sphere, transform streaming (`set_matrix`/`batch_update`) and animation playback now mark the bounds dirty so the sphere refits on the next frame — a fast mover can no longer outrun a stale sphere into the near plane (the 30-frame cadence remains as fallback). Result: the static sawtooth is gone (solid return-leg surface) and sweep shimmer drops to near-baseline with residual flips confined to grazing silhouette edges.
- **`strand_collapse` engagement gaps at these sites diagnosed — left as is.** Gate-level tracing (verbatim-extracted production functions) shows each worst site dies at a *different* gate: ≥150° corners on the fold-separation cap (`FOLD_SEP_FACTOR = 0.5`; the chamfer-strand fold separation saturates at 0.625·max(W,H), so ~0.65 would admit them — but 0.5 was deliberately chosen to kill bulb cross-link membranes, so it is not a free knob); layer hops structurally (the genuine fold crossing sits ~H/2 from the corner — an index gap of 1–2 on realistic sampling, inside the `MIN_GAP = 4` dead zone at any setting); retraces structurally (coincident legs form a distance *plateau* with exact ties, so a strict local minimum never exists — and a point-snap is the wrong repair for a continuous coincidence; the deposition bias above is the intended fix there). The corner fixes in this release remove the artifacts at exactly the sites collapse could not reach; `strand_collapse` keeps its default-off, 90–120° fold-removal role unchanged.
- Internal: the LOD worker's three hand-mirrored ring-writing loops (build, hairpin sweep, caps) are replaced by the shared `writeRingVerts` / `writeCapRingVerts`, injected via `Function.prototype.toString()` like `computeMiterFrames` — the stride-3 miter layout therefore has a single source of truth on both threads.

### Picking

- **Interactive picking of a point *along* any polyline or parametric tube, reported back to Python and/or client-side JS.** Enable from Python with `ViewerClient.enable_polyline_picking(marker_color=..., threshold_px=...)` or `on_polyline_pick(callback)` (the latter also enables it); both replay automatically on browser reconnect. Once on, hovering near a pickable object glides a screen-constant marker to the closest point on its spine and shows a cursor readout of the arc-length fraction; a left click that isn't a drag dispatches `{id, kind, fraction, point, local_point, segment, t}` to every registered callback, where `kind` is `"line"` or `"tube"` and `fraction` is the headline value (position in `[0, 1]` along total arc length). **Movement is continuous — the marker never snaps to vertices.** Picking is a two-stage hit test, applied identically to fat `Line2`, native `THREE.Line`, and parametric-tube geometry, owned by the in-file `PolylinePickController` (alongside the other viewer-global controllers): **(1) select** the nearest spine segment by 2D screen distance — every node is projected to pixels and the cursor's closest segment wins, so at a shared node segment *i* ends (t→1) exactly where *i+1* begins (t→0) and the hand-off is seamless instead of clamping to vertices the way a per-segment 3D closest-point does; **(2) place** the point on that segment via the 3D ray↔segment closest-point (`THREE.Ray.distanceSqToSegment`), because a screen-space parameter foreshortens under perspective (equal pixel spacing ≠ equal world spacing) and would quantize the marker toward the nearer endpoint — the world-space parameter keeps it exactly under the cursor and the arc-length fraction metrically honest. The fraction is read off a retained CPU copy of the local spine points (`userData.pickPoints`) plus a lazily-built cumulative arc-length table, so it is exact regardless of sampling density and regardless of the raycaster's reported hit. The per-object gate (how close the cursor must be) is `threshold_px + halfLineWidth` for a line; for a tube it is `threshold_px + beadHalfExtentPx`, where the bead's half cross-section (`max(width, height)/2`, plus any `anchor`/`height_offset`) is projected to pixels **per node** from that node's view-space depth — so a click anywhere on the bead *body*, not just its centre-line, registers, while the resolved point still sits on the spine. **For a tube, `pickPoints` is the full-resolution spine (1:1 with the per-spine-point arrays passed to `add_parametric_tube`, independent of LOD simplification), so `segment` is a direct index into the caller's per-point data dimensions** — the basis for looking up other dimensions (width, feed rate, curvature, …) at the picked point without shipping them to the browser. Picking is **opt-out per object**: `add_polyline` and `add_parametric_tube` take `pickable=True` by default; pass `pickable=False` to exclude that one object from hit-testing — it is then simply absent from the pick loop (still rendered, just never a pick target), so a busy scene can keep picking confined to the objects that matter. **Adding objects costs nothing when picking is never used**: a never-enabled picker never reads `pickPoints`, the loaders only stash references to arrays already held (the polyline's point buffer; a tube's full-resolution spine + the width/height arrays — no copy, no loop), and a tube's per-node bead half-extents are built lazily on the *first* pick rather than at load time. Picking is otherwise inert (zero per-hover raycast cost) until enabled. The marker lives in the scene like the pivot marker (not in `_objects`) so it can't be picked and survives `clear`. The trade-off of screen-space selection is no depth ordering between overlapping objects (screen-nearest wins) — picking already ignored mesh occlusion, so this only affects the rare overlap case. `disable_polyline_picking()` turns it off; callbacks run on the WebSocket receive thread and may re-enter the client (e.g. `add_sphere` from inside a pick callback). New demo `examples/22_polyline_picking.py` puts five distinctly-coloured objects in a grid — a 4-corner **square** (the clearest proof of continuous, snap-free motion; corners at 0.25 / 0.50 / 0.75 / 1.0), a **mixed-detail** line (sparse straight runs + dense coils + a ripple), a dense self-overlapping **spiral vase** (the ball-of-yarn toolpath from example 20), a parametric-tube **bead**, and a grey **circle** added with `pickable=False` to show the opt-out — the four pickable at once, with a callback that logs each pick (INFO summary + DEBUG raw payload) and drops a sphere coloured to match the picked item on the spine (browser → Python → browser round trip). Regression covered by `tests/test_browser.py::test_polyline_pick_roundtrip`, `::test_polyline_pick_disabled_by_default`, `::test_polyline_pick_between_nodes_no_snapping` (asserts a ~30%-along click resolves to an interior fraction, not a snapped vertex), `::test_parametric_tube_pick`, `::test_polyline_pick_pickable_false`, and `::test_parametric_tube_pickable_false` (each asserts a `pickable=False` object yields no pick yet stays in the scene).

A new viewer-global `DepthCueController` (in-file, alongside `ShadingDebugController`) restores depth on otherwise-flat polylines via two composable cues. `D` toggles **distance fog** — classic CAD depth cueing, distant lines dim toward near-black via `THREE.Fog` whose per-frame near/far track the scene bounding sphere and camera distance (`LineMaterial.fog` is flipped on for fat polylines since it defaults off; `LineBasicMaterial` defaults on). `Shift+D` toggles **eye-dome lighting** — a screen-space EDL post-process (Potree / CloudCompare style) that darkens each fragment in proportion to how much farther it sits than its four screen-space neighbours in log-depth, sculpting line bundles into legible 3D while passing background fragments through untouched. The two **compose**: fog dims globally, EDL adds local crossing contrast. A bottom-centre toast names the active state for ~1.4 s. Both are also reachable from Python via `ViewerClient.set_depth_cue(fog=None, edl=None)` — each bool toggles its cue, `None` leaves it unchanged — so a script can open straight into fog + EDL without the user touching the keyboard. EDL lazily builds an `EffectComposer` (`RenderPass` → EDL `ShaderPass` → `OutputPass`); the shared `DepthTexture` is attached to `renderTarget2` **only** — because `RenderPass` always renders into the composer's read buffer (`renderTarget2`, stable since the three-pass pipeline makes an even number of swaps per frame) and attaching the same depth texture to `renderTarget1` as well would form a GL feedback loop when the EDL pass writes `renderTarget1` while sampling it. `OutputPass` re-applies tone mapping + sRGB (the scene renders linear into the half-float target, and the renderer forces `NoToneMapping` for off-screen targets), so the runtime-configurable tone-mapping (`E` panel) still applies under EDL. **Fog composes with EDL via the EDL fragment shader itself, not the scene render:** `scene.fog` does *not* reach line fragments through the composer's `RenderPass` (it dims them in the direct render but is lost once the scene routes through `EffectComposer`), which would otherwise wash fog out entirely under the overlay. The EDL pass therefore re-applies linear fog from the depth it already samples — `mix(edlShade(color), fogColor, smoothstep(fogNear, fogFar, viewZ))`, matching three.js's linear-fog math — with `fogMode`/`fogColor`/`fogNear`/`fogFar` uniforms driven each frame from the active `scene.fog`. The render loop routes through the composer only while EDL is active and otherwise renders directly; the fog-range and toast updates run from a per-frame `DepthCueController.update()`, and the composer is resized from `DepthCueController.onResize`. New demo `examples/20_line_depth_cues.py` draws a ripply spiral-vase toolpath as one rainbow (`turbo`-colormapped) native polyline (`fat=False`, see below) and opens straight into fog + EDL via `set_depth_cue(fog=True, edl=True)`.

- **`add_polyline(..., fat=False)` renders a native `THREE.Line` instead of a fat `Line2`, for million-point toolpaths.** The default fat path (`Line2` + `LineGeometry` + `LineMaterial`) makes every segment an *instanced quad* — at multi-million-point counts that is ~6 vertex-shader invocations per segment plus real fill area, and it becomes the frame-time bottleneck for the worst-case "ball of yarn" toolpaths that fall back to flat line drawing. `fat=False` builds a plain `THREE.BufferGeometry` (`position` + optional `color` attribute) rendered as a native GL line: **one vertex per point, one draw call, ~1px wide** — dramatically lighter (1M points stays interactive). The trade-off is that WebGL clamps native line width to 1px, so `line_width` is ignored; fog and EDL need no width, so both depth cues still apply. Per-vertex `colors` / colormaps work identically on both paths — native lines store a `color` `BufferAttribute` and the GPU interpolates it along each segment. `set_draw_range`, the `draw_ranges` animation channel, `update_polyline_colors`, and `query_scene` all handle native lines via a `totalPointCount` + `geometry.setDrawRange` mechanism (vs the fat path's `instanceCount`), checked ahead of the generic `isPolyline` branch since native lines carry both `userData` flags.

### Parametric tube

- **`strand_collapse` now rejects fold snaps whose target lands more than `max_snap_factor · max(W, H)` from a ring's mitered baseline (default factor 1.0).** The 0.0.29 cross-link guard caps the *spine-endpoint* separation (`‖spine[j] − spine[i]‖ < 0.5 · min(max(W,H))`) but the *snap target* — the seg-seg midpoint between offset strand polylines — is unbounded by that test. Measuring against the rendered position (not `spine[r]`) is what the user means by "ring moved one bead-width" on `anchor="top"` tall beads. Configurable per call via `strand_collapse={"max_snap_factor": N}`; `strand_collapse=True` keeps the 1.0 default. Threaded through the worker plumbing (`init`, `collapseOnly`, and the LOD-rebuild collapse pass) and through Python via `_serialize_strand_collapse` (which also rejects unknown keys, non-positive factors, and non-numeric values with `ValueError`). ## 0.0.29

### Fixes

- **`strand_collapse=True` no longer paints a flat triangulated "diamond" across multi-corner spans on real-world toolpaths.** The seg-seg distance² grid that drives fold-target detection (introduced in 0.0.25) finds strict local minima below `(0.04·max(W,H))²` and snaps rings `(i+1..j)` to the closest-pair midpoint — on a constant-width sharp inside corner that's exactly the V-crease it was built for. On a real-world print path the inside-bend strands at two *different* corners — e.g. the two ends of a small star-shaped infill stitch, or either side of a bead width-bulb feature — can coincidentally land within tol of each other in 3D and produce additional spurious local minima at spine-spans of 7–41 segments. Snapping every ring in that long range to a single midpoint zips a flat triangulated membrane across entire toolpath features instead of folding a single crease — the "polygon-closing" diamond reported on ribweaver's `tube_8f5bba97` bead. Two guards now run on every detected fold target before the snap fires. **Spine-endpoint separation cap** — reject if `‖spine[j] − spine[i]‖ > 0.5 · min(max(W_i,H_i), max(W_j,H_j))`. A genuine fold has the spine bending back near itself even when arc-length between i and j is large (a tight hairpin returns to its entry); a cross-link spans multiple corners and the spine ends up far from where it started. Scaling by the *narrower* endpoint's bead dim — not the global `maxDim` — pins the cap to the bead's nominal half-width on width-varying paths so the cross-link cannot slip through when one endpoint sits at a width peak. **Peak vertex-turn cap** — reject if the maximum per-vertex turn inside `(i+1..j)` is below 8°. Catches a separate class of false positives where the strand polyline self-intersects from width swelling alone (the offset frame rotates as the bead widens) with no actual sharp corner on the spine — snapping in that case yields a coincident-vertex cluster with no geometric meaning. Per-vertex turn is precomputed once per `collapseTubeStrandFolds` call into a `vertTurn` array so each fold-candidate test is a plain O(span) range scan. Both guards also run inside the LOD worker on every reduced-spine rebuild, so creases stay correct at every camera distance. Documented in `repro_min.py` at the repo root — a self-contained 100-spine-point bead sliced from the original 13165-point ribweaver dump that triggers the diamond when `strand_collapse=True` and renders cleanly with the guards in place. Behaviour on existing examples and on constant-width sharp corners (the regression case the original 0.0.25 pass was built for) is unchanged.
- **`strand_collapse=True` on wide beads at sharp inside corners no longer renders a "cube + spokes" cluster of distinct vertices at the V-crease apex.** The diamond/cross-link guards above protect against false-positive folds across multi-corner spans, but the per-fold-target snap still leaves the inside-bend cross-section vertices at slightly different 3D points per strand — strand k's seg-seg midpoint is computed from k's own offset polyline, and on wide beads (W/H ≈ 7+) the chamfered-hex cross-section's three inside-bend strands stack vertically by ≈ H/2 at the snap target. The result is a small cube of coincident-but-not-identical apex points connected to the surrounding mesh by a fan of "spoke" triangles — visible on ribweaver's `tube_8f5bba97` at the bulb feature where the spine completes a 90° turn over six spine vertices. The collapse pass now runs in four phases: **(1)** detection unchanged (per-strand seg-seg local minima with the cross-link and peak-turn caps from the prior bullet) but each surviving fold target is buffered, not snapped immediately; **(2)** union-find clustering across cross-strand fold targets whose `(i,j)` ranges overlap (same-strand local minima are *not* merged — they correspond to genuinely separate bends and would zip up the spine between two corners); **(2b)** range-adjacency merge across clusters whose ring ranges begin within 2 rings of each other — a continuous bend distributed over many spine points splits across multiple clusters because the seg-seg stencil produces separate local minima per sub-region of the bend, and a strand whose polyline self-intersects *twice* through the bend would otherwise orphan its second half into a single-strand cluster; **(2b')** range extension outward while the adjacent ring's per-vertex turn exceeds `MIN_FOLD_PEAK_TURN/2` (capped at 5 rings per side) — picks up trailing high-turn rings the seg-seg stencil missed because it pinned the local min to one part of a continuous bend, so the boundary fan triangle at `iLo`/`jHi` lands on a low-curvature ring instead of bridging the bend's sharpest curvature; **(2c)** cross-section neighbour expansion — for each surviving cluster, add cross-section neighbours of already-clustered strands whose un-mitered offset has a positive dot product with the `spine→apex` direction (the dot-product formulation is independent of bend magnitude, unlike a distance-based test, so it works equally on sharp 90° corners and gentler bends). Phase 3 snaps every clustered strand across the union ring range to the cluster's averaged apex; a 2-strand wedge guard rejects any cluster that survives the merge with only one strand left (a single-strand collapse always produces an overlapping wedge cross-section — leaving the strand at its natural mitered position is the lesser visual evil). Both the main-thread call and the LOD worker's reduced-spine rebuild use the four-phase pass, so creases stay correct at every camera distance.

## 0.0.28

### Fixes

- **Read-side messages arriving during a binary load are no longer silently dropped.** The eight handlers that look up `this._objects.get(id)` — `set_color`, `set_opacity`, `set_visibility`, `update_transform`, `set_draw_range`, `set_clip_time`, `update_polyline_colors`, `update_parametric_tube_colors` — used to silently no-op when their target was still loading because the four binary loaders (`add_model_binary`, `add_polyline_binary`, `add_mesh_binary`, `add_parametric_tube_binary`) spawn a fire-and-forget `(async () => {...})()` IIFE that does `fetch` + geometry build + `_objects.set(id, obj)`. The WebSocket dispatcher falls through the case's `break` immediately, so any subsequent message targeting the same id is processed *before* the IIFE registers the object. The result was undefined behaviour: cold HTTP roundtrips lost the race (silent drop), warm caches or pre-existing objects won it (applied). The race masqueraded as "GLB native materials" in cold-load paths because `set_color` traversal over a missing target is unobservable. Fix: per-id in-flight deferred tracking (`this._inflightLoads`). Each binary-loader case branch synchronously installs a `_makeDeferred()` keyed by id before spawning its IIFE; the IIFE resolves on successful registration and rejects on error, stale token (load superseded by a newer add with the same id), or mid-load `_deleteObject`. `_addObject` returns the registered object (instead of `void`) so `add_model_binary` can verify *its own* load did the registration before stamping `blobUrl` and resolving queued ops — under a delete-and-re-add race, reading `_objects.get(id)` after `await _addObject(...)` could otherwise return a newer same-id object that won the await race, and queued ops would replay onto a load they didn't target. The new `_withObject(id, opName, fn)` helper applies `fn` synchronously if the object is registered, defers onto the in-flight promise otherwise, or silently no-ops if neither (matches today's behaviour for genuinely missing ids). Handler exceptions are caught at this dispatch boundary in both paths and surface as a single `console.error` — an uncaught throw in the deferred path would otherwise become an unhandled promise rejection. On load failure / cancellation, queued ops drop with a single `console.warn` naming the op and id. The eight cases route through `_withObject` at the case-branch level only — the private helpers (`_setOpacity`, `_setVisibility`, `_setDrawRange`, `_updateTransform`, `_setClipTime`) keep their "obj exists or skip" semantics so animation appliers and `_batchUpdate` aren't impacted. Parallel binary fetches are preserved (no IIFE-level `await` in the dispatcher). Ordering between queued ops is FIFO via microtask scheduling — two `set_color` calls during a load apply in the order they arrived. `_deleteObject` rejects any in-flight load for the id so queued ops on a deleted target drop cleanly; binary loaders pass `preserveInflight: true` through `_addObject` → `_deleteObject` so their own pre-registration cleanup doesn't reject the deferred they just installed. Regression covered by `tests/test_browser.py::test_set_color_during_binary_load_is_honoured`, `::test_set_visibility_during_binary_load_is_honoured`, `::test_set_opacity_during_binary_load_is_honoured`, `::test_update_transform_during_binary_load_is_honoured`, `::test_set_draw_range_during_binary_load_is_honoured`, `::test_two_queued_set_colors_apply_in_order`, and `::test_delete_during_binary_load_drops_queued_ops`. `set_clip_time` shares the same `_withObject` dispatch path; it is not given a dedicated regression test because the in-tree fixtures don't include an animated GLB.

## 0.0.25

### Parametric tube

- **`strand_collapse=True` flag on `add_parametric_tube` removes self-intersecting strand folds at tight inside corners.** Miter framing fixes the *outside* of a sharp corner but not the inside: when local curvature κ exceeds 1/half-width, the inner offset surface self-intersects geometrically and the renderer paints overlapping triangles that no frame trick can repair. The fix runs a per-strand fold detector + snap pass — independently per cross-section vertex k (six per ring on the chamfered hex). For each strand it builds the un-mitered polyline `strand[i] = spine[i] + u·U[i] + v·V[i]`, walks every segment pair `(i, j)` with `j − i ∈ [4, 50]`, and computes the 3D segment-segment shortest-line distance². A *fold target* is a cell `(i, j)` that is a strict local minimum of that distance² grid (vs. its 8 in-window neighbours) AND below `(0.04 · max(W, H))²`. For each fold target, the rings `(i+1..j)` of strand k snap to the closest-pair midpoint of the actual *mitered* mesh segments — geometric truth lives in the un-mitered strand (where miter inflation can't synthesise spurious local minima), but the snap target lands inside the real mesh. Coincident strand vertices give zero-area triangles in the two columns adjacent to k; the GPU culls them in hardware, so no re-triangulation is needed and the index buffer / normals / colors stay intact. **Coverage preservation is structural:** on the inside of any bend only the inside-side strands fold (that's the whole point of the local-min test), and the outside tip strand defines the top-view silhouette — it's never moved, so the bead footprint never shrinks. Endpoints are clamped to `[1, nSpine-2]` so revolution caps stay anchored. The work runs on the LOD worker via a `'collapseOnly'` postMessage after `buildParametricTubeGeometry` returns — the main thread never blocks on the O(nCs · nSpine · WIN) scan, and tube creation is non-blocking even at 130k samples (≈ 1.3 s of background work). For tubes that engage LOD reduction, the same collapse runs again inline on every reduced-spine rebuild, so creases stay crisp at every camera distance. A spine-distance pre-filter (kMax) shaves another ~10–12% off realistic-density bench cases by skipping segment pairs whose endpoints are already too far apart in 3D to fold. Off by default — opt in per call: `v.add_parametric_tube("bead", spine, widths, heights, strand_collapse=True)`. Showcased in `examples/21_tube_corner_zfight.py` (three-tube oracle: baseline + sphere markers, client `strand_collapse=True`, Python-built reference mesh — middle and right should match at every collapsed corner). Microbenchmark with kMax + streaming variants in `bench/strand_collapse_bench.mjs`.

## 0.0.24

### Parametric tube

- **Miter-joined cross-section frames at interior spine points.** Previously the ring at each spine point was placed perpendicular to the central-difference tangent with uniform cross-section dimensions, which collapsed two failure modes onto wide beads around sharp corners: (a) a fan of triangles exploding off the outside of the corner as adjacent frames rotated through large angles between closely-spaced samples, and (b) an inside crease where the rings' inner edges penetrated each other. The frame derivation now matches what 2D stroke rendering does at a miter join — tangent is the unit bisector of the incoming/outgoing segment directions (not the central-difference average, which diverges for unequal-length neighboring segments), and the cross-section's width axis is scaled by `1 / cos(half_turn_angle)` so the outer surface stays at constant half-width from each adjacent segment's centerline. Past a miter limit of 4 (SVG default), corners fall back to scale = 1 — strictly no worse than the pre-miter build at near-hairpins where the bisector is anyway ill-defined. The miter scale is applied only to position writes; normals continue to use the orthonormal `U, V` frame, so shading of the miter patch is correctly the bisector of the two adjacent-segment surface normals without any extra work. Build overhead on a 1M-point tube is ~16% (48 ms → off the main thread via the LOD worker for any tube ≥ 25k points, so not a UI hit in practice). `add_parametric_tube(orientations=...)` overrides bypass miter entirely — explicit per-point quaternion frames are used as-is and miter scale is pinned to 1.
- **Twisted tube at 180° tangent reversals fixed.** Spines that hairpin back on themselves (retrace, zigzag infill) produced a self-intersecting figure-8 twist across the reversal. Constant-up frames derive `U = V × T`, so when `T` flips sign `U` flips too and adjacent rings indexed their cross-section vertices at opposite physical points. The frame-build now sweeps `localFrames` after the main loop and — where `U_i · U_{i-1} < -0.95` — negates `U` on that ring and rewrites its vertices. `V` is untouched (even in `T`), so no cascading changes; the sweep is sticky, so the whole return leg stays aligned with the forward leg. Mirrored in the LOD worker so reduced and full-resolution geometries agree at reversals. Threshold `-0.95` restricts the flip to true hairpins — gradual curves and non-reversal sharp corners stay untouched. Skipped when the caller supplies explicit `orientations`. Revolution caps and the animated end cap now read tangent from the precomputed central-difference array instead of deriving `T = U × V`, so caps on retraces no longer extrude backward into the tube body. `examples/20_toolpath_zigzag.py` covers the regression — a C-shape retrace and a six-pass zigzag infill.

Lifts above the animation toolbar via a `--tjsv-anim-lift` CSS variable (cached to avoid per-pointermove `offsetHeight` reads).

### Fixes

- **`camera_lookat` tracking no longer no-ops.** The custom `ViewerControls` introduced in 0.0.20 deliberately never calls `camera.lookAt` inside `update()` to preserve its click-to-pivot guarantee — but stock `OrbitControls` used to do that re-orient implicitly, so the lookat branch in `_applyCameraTracking` had been silently relying on it. The orbit target was being moved to the tracked object each frame, but the camera was never re-oriented, so the view stayed pointed wherever it was before playback started. Now re-orients explicitly in the lookat branch, matching the precedent already in `CameraController`. `camera_follow` is unaffected — it translates camera and target by the same delta and preserves the view offset without needing a re-orient.

### Viewer display and controls

Pass `ViewerClient(tone_mapping_exposure=1.5)` to restore the previous look.
- **Runtime lighting panel (`E` key or `☼ E` toolbar button).** Four live controls — tone-mapping mode (`none` / `linear` / `reinhard` / `cineon` / `aces` (default) / `agx` / `neutral`), tone-mapping exposure, environment intensity, ambient intensity. Values are applied live and persist across reloads in `localStorage` under the `tjsv.` namespace. A Reset button restores the page-load baseline (URL param > options > hard default, skipping localStorage) and clears the four persisted keys. Changing the tone-mapping mode flushes every material's shader (`material.needsUpdate = true`) because three.js bakes the tone-mapping constant into the compiled program — expect a one-frame recompile stutter on very large scenes.
- **`ViewerClient` accepts four lighting kwargs**: `tone_mapping`, `tone_mapping_exposure`, `environment_intensity`, `ambient_intensity`. Precedence for initial values: **URL param > `ThreeJSViewer` option > `localStorage` > hard default.**

### Parametric tube LOD

- **Attribute-aware RDP simplification.** Parametric-tube LOD previously measured perpendicular distance in 3D only, so attribute variation on a geometrically straight segment (a colormap gradient, a width bump on a flat line) was invisible to RDP and would collapse — `LOD_MAX_SKIP=100` was a blunt safety valve that inserted a midpoint every 100 collapsed points to hide the worst banding, without knowing how variable the attribute actually was. The worker now projects into an augmented space (xyz + weighted width, height, r, g, b) so a single camera-scaled epsilon bounds geometric *and* attribute error together: colormap gradients and width ramps survive simplification at the same sub-pixel threshold as geometric detail. Internal weights: width/height contribute 0.5 world units per unit of delta; a full per-channel color swing costs 5% of the tube's bounding radius (which now includes the max cross-section half-extent, so thick tubes with a compact spine don't under-weight color). `LOD_MAX_SKIP` is kept as a safety valve but should rarely fire. The sync fallback (used for the first render before the worker is ready) mirrors the worker's logic so the initial LOD matches subsequent worker-produced levels.
- **`update_parametric_tube_colors` invalidates the LOD chunk cache.** Chunk splits depend on color deltas under augmented-space RDP, so a color swap mid-animation now rebuilds affected chunks instead of reusing stale simplifications.

### Docs

- **Embedding contract documented.** The viewer issues a no-cors HTTP GET against `wsUrl` (scheme swapped to http/https, path+query preserved) before each WebSocket attempt to suppress the browser's unsilenceable "WebSocket failed" console warning. Embedders pointing at a non-`websockets` server need the host (or its proxy) to answer *something* on that GET (200/400/404/426 all count) or the probe never resolves and the WebSocket is never attempted. Previously only explained by a one-line code comment; now covered in `ThreeJSViewer` JSDoc, the probe-site comment, and a new "Embedding the Viewer" section in `DESIGN.md`.

### Internal

## 0.0.20

### Animation lifecycle

- **`load_animation` preserves playback state on subsequent loads.** The first call to `load_animation` (when no animation is loaded) still starts at t=0, with playback controlled by `autoplay` (default `True`; pass `autoplay=False` to load paused). But a *subsequent* call (one already loaded) now preserves the current playhead time (clamped to the new duration), play state, and camera-tracking — only the underlying frame data is swapped. This makes the "swap mid-playback" pattern (reconcilers, tab switches between related animations) flicker-free without any caller bookkeeping. ## 0.0.19

### New features

- **Animation interpolation** — animation playback now lerps/slerps between keyframes by default, so producers can sample at the signal's bandwidth (e.g. 10 Hz) and still get smooth 60 fps playback. Translations lerp, rotations slerp, float channels (`draw_ranges`, `opacity`, `clip_times`, scripted `camera_target`/`camera_position`) lerp element-wise, and the `colors` channel lerps hex values in 8-bit RGB space (works for direct hex and colormap-indexed `uint8`). - **Transform on `add_model_binary()`** — `position`, `rotation`, `scale`, and `matrix` parameters applied after async model load completes (fixes race condition)

- **Correct transparency rendering across all object types** — opacity now plays well with depth sorting on primitives, meshes, and GLB models (including GLBs with multi-material arrays, which previously crashed on material updates). ## 0.0.3

Refactors animation to use generic binary channels, replacing the hardcoded transform/draw_range system with an extensible channel-based architecture. Any per-object-per-frame data can now be sent as a typed binary channel.

### Changes

- **Generic binary animation channels** — `animation.add_channel(name, object_ids, data, dtype, stride)` can carry any per-object-per-frame data as a typed binary channel. `set_transform_data()` / `set_draw_range_data()` are kept as convenience wrappers.
- **New channel types** — `colors` (uint32), `visibility` (uint8), and `opacity` (float32) channels join the existing `transforms` and `draw_ranges`
- **Clearer errors on bad channel data** — `add_channel()` raises on an unsupported dtype (allowed: float32, uint32, uint8) instead of letting it reach the browser; the viewer logs and skips unknown dtypes instead of crashing playback

### Updated examples

- Existing examples updated to use the new `add_channel()` API where appropriate
